MCP Token Usage Reduction

Cutting the token cost of Tasker's most-called MCP tools by sending shared project context once per session instead of on every call.

TDE-371  ·  folds in TDE-319  ·  shipped & deployed 2026-07-06

Executive summary

Every get_task call was re-shipping the same ~1,700 tokens of project-wide context — the Foundation, the full Instruction Set, and the Knowledge Base index — even though the calling agent already had it in context from earlier in the session. The fix sends that shared context once per project per session, then replaces it with a short pointer on every subsequent call.

Why it matters

Token economy is the hinge of Tasker's whole value proposition: durable, shared, quality-gated state only beats an agent re-deriving context from scratch if injecting that state is cheap. Every wasted token on a repeated context dump weakened the core argument for using Tasker over a platform's native, ephemeral task tool.

The problem

On every single get_task, the server appended three blocks unconditionally:

  • Project Foundation — goal, intent, scope, definition of done, risks.
  • The full Instruction Set — every project rule (task format, code style, deployment, positioning).
  • The Knowledge Base index — the title of every KB entry (62 on a mature project).

These three blocks are identical for every task in a project. Opening ten tasks in a session shipped that same ~1,700-token payload ten times — nine of them pure waste, because the agent already held it in its context window after the first.

The reduction is therefore not compression or truncation. It is de-duplication across time: send the shared context once, then stop.

How it's implemented

The core constraint: the MCP protocol carries no session ID. A request only identifies a user (via API key). So "has this agent already seen the context this session?" cannot be read directly — it has to be inferred. Four pieces do that:

  1. A tracking table. mcp_context_primed holds one row per (user_id, project_id) with a primed_at timestamp — the server's memory of "I already sent this user the heavy context for this project."
  2. A per-call decision. On each get_task, send the full context if — and only if — refresh_context was passed, or no priming row exists, or the row is older than 3 hours. Otherwise send the compact pointer. When full context is sent, the priming row is written (fire-and-forget, so it never slows the response).
  3. A session boundary. __init_tasker_session — which agents call at the start of a session — deletes the user's priming rows, so a fresh session re-primes on its first get_task. The 3-hour window is a backstop for agents that never call init.
  4. An escape hatch. get_task(refresh_context: true) forces the full context back inline — for when an agent's context window was compacted and it genuinely lost the earlier blocks.

Companion change — get_project (folds in TDE-319)

get_project was the other overflow source: it dumped every task's Notes (the detail field), which is the bulk of a large project's payload. It now omits Notes by default — keeping the full task map (IDs, titles, statuses, sections) — and restores them only when called with include_notes: true. A marker line tells the agent the Notes were dropped and how to fetch them.

The compact tier never touches task-specific content (title, status, detail, milestones, review verdict) — only the repeated project-wide boilerplate is replaced, with this pointer:

Foundation, Instruction Set, and the KB index for "…" were provided on the first task you opened here this session and are still in your context. Re-read on demand: get_project_foundation · get_project_is · list_kb_entries. To force the full context back inline, call get_task with refresh_context: true.

Nothing is ever withheld that wasn't already sent. First touch always primes, so an agent is never under-grounded. The one assumption is that the agent still holds the first-touch context in its window; if a compaction wipes it, the pointer names exactly which tool to call to pull it back.

Correctness & trade-offs

Every fallback is deliberately fail-safe — it errs toward sending more context, never less:

  • Fire-and-forget priming write. Two rapid back-to-back calls could both see "not primed yet" and both send full before the row lands. Worst case: context sent twice. Never: context missing.
  • Concurrent clients. Two agents on the same user+project share priming state, so one might get compact for context the other primed. Rare for solo-dev usage; the escape hatch and __init reset cover it.

Scope: who benefits, and how much

The change is global — a new mcp_context_primed table in production and a redeployed MCP function — so it applies to every user, not a single account. The mechanism is identical for new users, and first-touch grounding always happens, so no one is under-grounded.

But the magnitude of the saving scales with how much context a project has accumulated. A brand-new project has little Foundation, only a baseline Instruction Set, and an empty KB — so there is almost nothing to suppress, and full ≈ compact. The benefit compounds as the project grows — which is exactly where the "too expensive" problem actually bites.
