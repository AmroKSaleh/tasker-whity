Scope — read first. This covers flow authoring only (build_new_flow → create_task → set_task_output/input → flow IS/KB → name_flow → get_flow_order). It does not cover execution (run_flow, the judge loop, regenerate/escalation) — the flow was authored but not yet run. The most important questions (does the validation loop actually catch bad output? how do contracts behave under regeneration?) need a second report after execution.

What worked well

Keep these.

Positive · P1Contract rule-quality linter is the standout

On set_task_output/set_task_input, vague judgment language ("relevant", "readable") was flagged at authoring time with a concrete rewrite example. It caught two soft rules I'd have let slide. This is the single best part of the authoring UX — it enforces the discipline that makes contracts worth having.

Positive · P2Output/input split + fan-in is clean

Def-of-done (set_task_output) modeled separately from acceptance criteria (set_task_input, one call per source) made the fan-in on TDE-266 (consumes 264 and 265) straightforward. Upsert-per-source semantics are intuitive.

Positive · P3Flow KB auto-loads on every task

Unlike project KB (on-demand), flow KB rides along on every get_task in the flow — ideal for carrying the design to each build step. It's also a live preview of why the judge feature needs reliable KB reads (TDE-254).

Positive · P4get_flow_order is a good final artifact

The numbered, dependency-aware view with the context bag inline is a clear "here's what you built" confirmation.

Frictions & gaps

Each: what happened → impact → recommendation.

Friction · F1No fast-path for arriving with a finished design

build_new_flow assumes a cold start and prescribes a grill-me interview. We had an approved spec, so the interview was redundant — and skipping it means the tool's own protocol wasn't actually followed.

ImpactRedundant interaction, or a silently-skipped protocol. RecommendationA mode that accepts a structured flow spec and persists it directly, or detects an attached design doc and switches to "review & persist".

Friction · F2Grounding dumps all project tasks

The project_context payload included all ~80 tasks regardless of relevance.

ImpactNoisy, token-expensive, scales badly. RecommendationRelevance-filter or cap the grounding (target section + goal-keyword match), or summarize by section with counts.

Friction · F5Step ordering interleaves phases

Phase-2's TDE-268 landed at step 4, ahead of Phase-1's TDE-267 at step 5, because 268 sits shallower in the graph — but 268 is blocked on TDE-254. The recommended order sequences a blocked later task ahead of an unblocked earlier one.

ImpactMisleading execution order; "phase" isn't expressible in the I/O graph alone. RecommendationA phase/group concept or soft-ordering tiebreaker; warn when a task with an unmet external blocker is ordered early.

Friction · F6Flow IS silently suppresses project IS

Creating the first flow IS flips the flow into "flow IS governs" mode, which replaces the project's non-universal IS (Code Style, Deploy Rules) for these tasks. I had to restate those rules to avoid the build tasks losing them.

ImpactA real footgun — critical operational rules silently vanish unless restated or universalized. RecommendationWarn which project IS entries will be suppressed and offer to copy them in; treat deploy/code-style as universal by default.

Friction · F7External / cross-flow dependencies aren't expressible

TDE-268/269 genuinely depend on TDE-254 (outside this flow). A real edge would pull 254 into this flow's connected component, so the dependency could only be documented, not enforced.

ImpactA hard prerequisite goes unenforced; the graph under-models reality. RecommendationA "soft"/external dependency edge that blocks without merging components — cross-flow dependencies as a first-class concept.

Friction · F8Authoring is protocol-dispenser only; nothing verifies it

Nothing checks that an interview happened, that every edge got a contract, or that contracts are non-trivial before name_flow.

ImpactFlow quality depends entirely on agent diligence. RecommendationA lightweight pre-name_flow check ("N edges have no contract; M rules are warning-flagged — proceed?").

Friction · F12Authoring overhead — ~27 calls for a 6-task flow

1 build_new_flow + 6 create_task + 7 set_task_output + 7 set_task_input + 1 name_flow + 3 IS + 1 KB + 1 get_flow_order ≈ 27 calls (plus 2 re-sets to fix linter-flagged rules).

ImpactHigh authoring cost; scales linearly with flow size. RecommendationA batch/transactional create_flow(spec) that accepts the whole structure in one validated call.

Smaller notes

Note · N1confirm_contract not exercised

All 12 contracts are "AI-QA'd" until human-blessed via confirm_contract. The flow was confirmed verbally, but no contract was blessed. Worth clarifying the UX difference between "flow confirmed" and "contracts blessed" (the latter is the moat per TDE-203).

Note · N2Duplicate sections in grounding

Two identically-named "Define docs structure… - Flow Tasks" sections appeared — pre-existing cruft from an earlier flow's task-filing. Suggests flow-task sectioning can create duplicates; worth a cleanup + guard.

Note · N3Re-set ergonomics

Fixing a linter-flagged rule meant re-sending the whole contract (set_task_output replaces). A per-rule patch would be lighter.

Top recommendations

Ranked for the Flows-optimization discussion.

  1. Batch create_flow(spec) (F1, F12) — biggest authoring-cost win; also gives a "persist a pre-designed flow" path.
  2. Warn on flow-IS suppression (F6) — prevents silent loss of deploy/code-style rules; low effort, high safety.
  3. External / soft dependencies (F7) — needed for any flow with real out-of-flow prerequisites; also unblocks honest phase-ordering.
  4. Relevance-scoped grounding (F2) — cost + scale.
  5. Phase/group-aware ordering (F5) — correctness of the recommended order.
  6. Keep & extend the contract linter (P1) — consider auto-suggesting the rewrite.
