What worked well

Positive · P1The adversarial validators earned their keep

Every step's validator verified against the live system — querying the remote DB, reading the deployed source, and calling the deployed tools over HTTP — not just trusting the artifact's self-report. On TDE-264 a validator caught a real problem (F3) and reopened the task. This is the core value: independent re-checking that doesn't take the builder's word.

Positive · P2The regenerate/reopen loop works exactly as designed

The live demo drove a blocker fail → task reopened with critique (action=regenerate) → fix → pass. And the flow's hard dependency enforcement kept steps in order. The machinery this feature reuses is sound — proven end-to-end.

Positive · P3"Verification over assertion" was enforced, not optional

Because each gate demanded evidence, every step was actually run before it could pass — migration applied + queried, tools called against the live endpoint, frontend built. The flow made me prove it, which is exactly the discipline that catches "looks correct but isn't."

Frictions & gaps

Friction · F3 (headline)A pre-authored gate rule over-reached into the consumer's territory

The 265←264 gate "helpers callable from the enable code path" was authored before implementation. But the enable path is what the consumer (265) builds — it can't exist at the 264→265 handoff. The adversarial validator correctly failed it (the helpers were complete), forcing a regenerate cycle to re-scope the rule. The rule was also ambiguous (capability vs. existing-caller).

ImpactA false-blocker cost a full regenerate cycle. The validator was right; the contract was wrong. RecommendationAuthor gate rules for what the producer hands over, not how the consumer will wire it. A contract-authoring linter could flag rules that reference the consumer's own deliverable.

Friction · F4The check-only "shortcut" ignores output self-check judgment rules

validate_output decides "all rules are check, use the one-call shortcut" based on the gate contract only. When the producer's output self-check contains judgment rules (it did, twice), they're invisible to that decision and would silently fall to self-grading. I hand-spawned validators to keep independence.

ImpactIndependence can be silently lost for output-side judgment rules. RecommendationThe shortcut decision must consider gate AND output self-check rule kinds together.

Friction · F2Duplicate rule IDs across gate + self-check corrupt the ledger label

Gate and output contracts both start their rule IDs at r1. On submit, the gate "collapsed them by ID" and surfaced a failure under the wrong rule's label (a "helpers" failure showed as "migration applied"). The validator had to explain the mismatch.

ImpactVerdict attribution is wrong when IDs collide — misleading critiques. RecommendationNamespace rule IDs (e.g. gate:r1 vs out:r1) or auto-assign globally unique IDs.

Friction · F1run_flow won't accept the flow's own short ID

get_flow_order shows the flow as TDE-F1, but run_flow(flow_id:"TDE-F1") returned "not found" — it only takes a UUID or name. I had to start it via a member task_id.

ImpactThe identifier the UI shows you is the one identifier the run command rejects. RecommendationResolve flow short IDs in run_flow (and everywhere a flow is addressed).

Friction · F6Rigorous execution is very token-heavy

Each step = deploy + live-test + store_artifact + complete + validate + a validator subagent (~30–44k tokens each); plus the regenerate cycle = 6 validator runs for 4 steps. The assurance is real but the cost is large and grows with flow size.

ImpactCost scales with steps × validators; a cheaper-model validator tier or batching matters. RecommendationAllow a cheaper model for validators; reuse one validator across a step's rules; cache live-checks.

Honest finding: "reuse" collided with the data model

Note · F9The judge mirrors the flow loop but doesn't literally reuse it

The flow IS said "reuse, don't rebuild." In practice the verdict needed its own store (review_bar / review_verdict) and its own submit (submit_task_review), because submit_validation_result writes to the flow/edge ledger, not a standalone task. So Phase 1 mirrors the loop (same shape: store → grade → gate → regenerate/escalate) rather than reusing the exact calls. A purer reuse would treat review_bar as the task's output contract and run the real validate_output/submit_validation_result — worth revisiting if duplication becomes a maintenance cost.

Did running it as a flow improve the output?

VerdictYes for confidence; the code itself was correct without it

The gates forced live verification at every step and the independent validators re-checked against the real system — that's genuine, and it's discipline I might have shortcut on a plain build. But the one thing the gates caught was a mis-scoped contract (F3), not a code defect; the code passed everywhere it was checked. So for this kind of work the assurance came mostly from "actually run it" (verification), which the flow enforced but doesn't uniquely provide. Net: high-confidence delivery, real cost, and the flow's contribution was forcing rigor + independent re-checks rather than finding bugs. This squares with the pre-build call: for code, verification is the real gate; flows add value by making it non-optional.

Top recommendations

  1. Contract-scope linter (F3) — flag gate rules that reference the consumer's own deliverable; the single highest-value fix (it cost a whole cycle).
  2. Shortcut must see output self-check rules (F4) — or independence silently lapses.
  3. Globally-unique / namespaced rule IDs (F2) — wrong-label verdicts are a correctness bug.
  4. Resolve flow short IDs in run_flow (F1) — small, obvious papercut.
  5. Cheaper validator tier + reuse (F6) — make rigorous runs affordable at scale.
  6. Revisit literal reuse of the validation ledger (F9) — reduce the parallel-path maintenance cost.
