# MCP: keyset cursor pagination pattern + new-tool restart gotcha + flow short_id lookup gap (TDE-378)

_KB entry · source: agent · READ-ONLY mirror (edit via create_kb_entry/update_kb_entry over MCP)._

Four learnings from building resolve_reference + list_tasks/list_kb_entries pagination (2026-07-31), each non-obvious enough to be worth a future session not re-deriving.

## 1. New MCP tools need a Claude Code session RESTART to become callable, even though the deployed function is already correct
Deployed `resolve_reference` and confirmed it via a direct `tools/list` call (public, no auth, sits before the auth check in index.ts) — 140 tools, correct schema, immediately. But within the SAME already-running session, `ToolSearch` couldn't find it at all, and returned STALE (pre-deploy) descriptions for tools that already existed (e.g. an old, un-trimmed `name_flow` description with citations already removed hours earlier). This confirms the deferred-tool catalog a running session holds is a snapshot taken at session start, not a live query against the MCP server — a deploy updates the server instantly but not an open session's view of it. Practical consequence: after adding or changing a tool's presence (not just its description text on an EXISTING tool — description edits on existing tools apparently do reach a running session's actual tool-call behavior, since list_tasks/list_kb_entries's new params worked live without a restart), a genuinely NEW tool name needs a restart before it can be invoked or behaviorally verified. Don't try to work around this with raw HTTP + a stolen bearer token — ask for a restart (per the existing "Restart CC" rule) and verify after.

## 2. A flow's own displayed short_id (e.g. "TDE-F1") could not be used as a lookup key ANYWHERE
Audited every `flow_id` parameter across the codebase before adding resolve_reference: every one resolves either a UUID or an `ilike('name', ...)` substring match. None ever did `.eq('short_id', ...)`. So the identifier Tasker shows the user for a flow was structurally unusable as an input to any tool — you could always look up a flow by name-guessing or by its opaque UUID, never by the short code a human would actually type. resolve_reference is the first place a flow short_id resolves correctly. Worth checking whether run_flow/get_flow_context/etc. should ALSO accept short_id directly as a first-class flow_id form, not just resolve_reference as a detour — not done in this pass, flagged for whoever extends flow lookups next.

## 3. Keyset (not OFFSET) cursor pagination pattern, now reusable
Added `encodeCursor`/`decodeCursor`/`applyCursor`/`clampLimit` near the top of index.ts (before PHASE_COLS). Keyset on (sortCol, id) via PostgREST's `.or('sortCol.gt.X,and(sortCol.eq.X,id.gt.Y)')` syntax — stays correct while rows are edited between page fetches, unlike LIMIT/OFFSET which skips or repeats rows under concurrent writes. Cursor is opaque base64 JSON `[sortValue, id]`. Wired into list_tasks (sort_order or updated_at) and list_kb_entries (created_at) as the first two; extending to other unbounded list_* tools (list_flows, get_task_history, get_flow_audit) is now mechanical — same four helpers, no new design.

## 4. Relationship filters over JSONB I/O edges can't be a single indexed WHERE — this bounds what "shared filter grammar" can cheaply express
Built `blocking` on list_tasks (TDE-556's fold-in — the motivating query was "tasks whose output feeds an unfinished task"): only tasks whose output is an input source (`inputSourceIds`) for at least one NOT-done task anywhere in the project. Because `tasks.input` is a JSONB column and the relationship is a REVERSE lookup (find producers referenced BY consumers, not a consumer's own forward edges), this can't be expressed as a single SQL WHERE with an index — it's computed by fetching the project's (id, input, status) rows and building a reverse index in JS. Consequence, stated in the tool description rather than left implicit: `blocking` disables cursor pagination for that call (the candidate set is filtered unpredictably before paging would apply) and requires project_id. Any future relationship filter over the I/O graph (flow membership, gate/contract state) will hit the same shape of constraint — plan for "fetch project-scoped, filter in JS, no pagination" as the default pattern for graph-relationship filters, not a bug to fix later.

Verification note: cursor pagination, updated_since, and blocking were all confirmed against the LIVE deployed function (two consecutive real pages with no dupes/gaps; a throwaway producer/consumer pair wired via set_task_input, deleted after). resolve_reference's logic was traced by hand against the real short_id regexes but could not be behaviorally called this session — see learning #1.
