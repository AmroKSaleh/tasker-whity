Found by direct measurement during the TDE-343 core-workflow pass on 2026-08-04. This is roughly 30x more expensive than the token optimization TDE-343 was proposing, which is why it is filed as its own high-priority bug.

OBSERVED: get_task's own tool description states the full project context is "normally sent only on the first task opened in a project each session, then omitted as a short pointer," with refresh_context offered for use after compaction. In one session, ten get_task calls were made against TDE (TDE-286, 279, 273, 260, 783, 807, 790, 816, 792, 343). EVERY ONE returned the complete payload: Project Foundation, the full multi-section Project Instruction Set, and the ~90-entry KB title index. Roughly 3k tokens each, ~30k tokens for the session, of which ~27k was redundant.

NOT A PARALLEL-CALL RACE: six of those calls (TDE-783, 807, 790, 816, 792, 343) were issued strictly sequentially, each in its own message after the previous had returned. The suppression still did not happen.

PAYLOAD SCALES WITH PROJECT SIZE, so the biggest project pays the most: a get_task against project AAA (no Foundation, small IS, no KB entries) returned a compact response. TDE — the largest and most-worked project — is the worst case, on every single call.

LIKELY ROOT CAUSE, UNVERIFIED — CHECK BEFORE FIXING: the MCP runs on Supabase Edge Functions, which are stateless per invocation. "First task opened this session" requires session memory the server may simply not have, in which case the tiering logic never had anything to consult and the "short pointer" branch is effectively dead code. Confirm this before designing a fix — do not assume.

WORTH DECIDING AS PART OF THE FIX: where the session boundary should live. Options include the client passing a flag (the agent knows whether it has already seen the context), a short-TTL server-side cache keyed by user+project, or making the omission explicit — a context:"pointer" parameter the caller opts into. The client-passes-a-flag option is the only one that works without server state, but it trusts the caller.

RELATED: TDE-371 shipped the get_task context tiering this bug says is not taking effect — start there and check whether it regressed or never worked in the deployed edge function. TDE-372 (MCP Token Usage Reduction Report) should cite this measurement rather than re-deriving it.

## SECOND INDEPENDENT REPRODUCTION 2026-08-06 — different project, same result, plus one new consequence

Reproduced on WQW (Waqtak Website) during a real working session, not a deliberate test. Confirms this is not TDE-specific.

### MEASUREMENT
Eight get_task calls (WQW-160, 137, 136, 158, 147, 174, 159). All eight returned the complete Foundation + full Instruction Set + KB index, byte-identical. refresh_context was never passed.

    per response                   ~4,600 tokens
    of which repeated boilerplate  ~3,000 tokens
    redundant repetitions          7
    wasted                         ~21,000 tokens

Against a total session Tasker spend of roughly 71,700 tokens, that is about 29% of everything Tasker cost and roughly 44% of all read cost.

### CORROBORATES THE PARALLEL-RACE RULING-OUT
Four of the eight (160, 137, 136, 158) went out in ONE parallel batch, so a race would explain those. But 147, 174 and 159 were separate sequential calls much later in the same session and also got the full payload. This matches TDE-870's original finding on six sequential TDE calls. Two projects, two sessions, both sequential and parallel paths: the suppression never fires.

### NEW CONSEQUENCE NOT YET RECORDED HERE — IT DEFEATS THE TAGS FEATURE
create_task takes `tags`, documented as "Tags used to filter which Instruction Sets are loaded into this task's context", and update_is_entry takes `tags` plus `universal`. So per-task IS filtering already exists as a product feature.

If the whole IS is re-sent unconditionally on every call, that filtering cannot deliver its benefit even for projects that configure it correctly. Whatever fix lands here should compose with tags: the once-per-session suppression AND tag-based selection need to work together, otherwise a well-tagged project still pays full price.

Concrete example from WQW: its IS is ~2,500 tokens, of which ~1,800 is a single "Article release flow is mandatory" entry. Seven of the eight tasks read this session were security, caching or DNS work. None of them needed the article publishing procedure, and all of them received it, every time.

### SECOND-ORDER EFFECT WORTH NAMING IN THE FIX RATIONALE
The cost scales with Instruction Set richness, so a project that invests in a thorough IS is penalised on every subsequent task read. That is a backwards incentive: the product asks users to encode governance in the IS, then charges them context for it repeatedly. Worth stating explicitly when justifying the priority of this fix.

[Merged from #874] get_task re-sends the entire Instruction Set on every call, against its own documented behaviour:
Known issue, filed 2026-08-06 with measurements from a real working session on the WQW (Waqtak Website) project. This is the single largest source of wasted context in Tasker usage as observed.

**The documented behaviour, from get_task's own tool description:**

"refresh_context: Force the full project context (Foundation, Instruction Set, KB index) back inline. Normally sent only on the FIRST task opened in a project each session, then omitted as a short pointer."

**The observed behaviour: it is sent on EVERY call.**

Eight get_task calls were made against WQW in one session (WQW-160, WQW-137, WQW-136, WQW-158, WQW-147, WQW-174, WQW-159). Every single response carried the complete payload:

    # Project Foundation                      (~250 tokens)
    # Project Instruction Set                 (~2,500 tokens)
      - Article release flow is mandatory     (~1,800 tokens on its own)
      - Waqtak is a queue management system only
      - Audience = businesses/operators
      - Brand voice & visual rules
      - Persist reached context into the task's Context
    # Project Knowledge Base — index          (~250 tokens, 16 titles)

refresh_context was never passed. The text was byte-identical across all eight.

**Cost measured on this session**

    per get_task response          ~4,600 tokens
    of which repeated boilerplate  ~3,000 tokens
    calls made                     8
    redundant repetitions          7
    WASTED                         ~21,000 tokens

Against a total session Tasker spend of roughly 71,700 tokens, that single defect is about 29% of everything Tasker cost, and roughly 44% of all read cost. Fixing it would drop read cost from about 48,400 to about 27,400 tokens.

**Ruling out the obvious explanation**

Four of the eight calls (WQW-160, 137, 136, 158) were issued in a single parallel batch, so a race on "have we sent this yet" would explain those four. But WQW-147, WQW-174 and WQW-159 were separate sequential calls made much later in the same session, and they also received the full payload. So this is not solely a parallel-execution race. Either the deduplication is not implemented on this code path, or the "first task this session" flag is not keyed on anything that persists across calls.

Worth checking whether the flag is keyed on the MCP session, the conversation, the project, or nothing at all.

**Why this matters more than the raw number suggests**

1. It scales with Instruction Set size, and the IS is the thing users are encouraged to enrich. A project that writes a thorough IS is punished on every subsequent task read. That is backwards incentive design.
2. It is invisible. Nobody sees a token counter, so the cost accrues silently. This issue was only found because a user explicitly asked for a usage audit.
3. It interacts badly with the tags feature. tags on create_task and update_is_entry already exist to filter WHICH Instruction Sets load per task. If the whole IS is unconditionally re-sent regardless, that filtering mechanism cannot deliver its benefit.

**Suggested fix, in priority order**

1. Make the documented behaviour real: send the full block once per session, then a short pointer such as "Project context already loaded this session. Pass refresh_context:true to reload." Ensure the flag survives parallel calls (set it optimistically before responses are built, not after).
2. Honour tags when composing the IS block, so a task tagged "security" does not receive a 1,800-token article publishing procedure.
3. Consider sending the KB index only once too. It is smaller but it is pure repetition as well.

**Verification**
Open three tasks in the same project in one session, one of them in a parallel batch. Only the first response should contain the "# Project Instruction Set" heading. Measure the payload of calls two and three; they should be roughly task-body-sized, not task-body-plus-3,000.

See also the companion task on get_project returning titles only.
