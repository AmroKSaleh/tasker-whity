The flow/dependency system currently only models DATA I/O: "task A's output feeds task B's input" (via input.source_task_id — single source, consumes output). It has NO concept of a pure BLOCKER: "this task must be done before that one / this task blocks others," independent of any data passing.

Two different relationships that should both exist:
- FEEDS (have it): A produces output → B consumes it. Data dependency.
- BLOCKS (missing): A must be resolved before B can start, even though B doesn't consume A's output. Precedence/gate.

Use cases the gap exposed (2026-06-02):
- Project-wide gates like "Start using GitHub" (TDE-174) — currently faked with a pinned rush task + an agent memory rule because the flow system can't express "blocks everything."
- One task blocking several, or a prerequisite that isn't a data producer.

Design considerations: support many-to-many blocker links (not just single-source like input); surface in Blueprint (different edge style/color from data flow); honor it in the same flow_blocked warning path as data deps. Relates to [[TDE-171]] (dependency enforcement is currently advisory/bypassable — a blocker concept is only as useful as its enforcement).
