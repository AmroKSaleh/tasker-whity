Split out from TDE-262 (Foundation/bootstrap_project shipped without this half). Let users define their OWN default Instruction Sets — reusable personal/org conventions (code style, deploy rules, tone, autonomy) — that auto-seed every new project beyond the built-in baseline IS.

Scope notes from the 262 discussion:
- IS only. Personal default KBs were deprioritized — KB entries are almost always project-specific, so a personal-KB-that-seeds-everything mostly seeds irrelevance (and KB-read budget is already a concern, see TDE-254).
- Phase 1 = personal (single user) defaults. Org/shared team defaults are Phase 2 B2B.
- Mechanism: a user-level store of default IS entries, applied at create_project alongside the existing baseline-IS trigger. The Foundation interview (bootstrap_project) can reference them when proposing project-specific IS additions.

WHY PARKED / what "doing it right" means (from the 2026-06-26 discussion):
- Thin marginal value as built: the built-in baseline ALREADY seeds the universals (task hygiene + working prefs). A user's other conventions (deploy rules, code style, stack) are mostly PROJECT-SPECIFIC — blindly seeding them into every new project is often wrong. And bootstrap_project already proposes project-specific IS at creation. So the "universal-to-user, not-in-baseline, not-project-specific" sweet spot is small.
- A proper design would likely distinguish: (a) universal personal conventions (truly always-on) vs (b) project TEMPLATES you pick at creation, rather than one blind auto-seed-everything bucket. Possibly integrate with the bootstrap IS-proposal step instead of a separate seed.
- Real payoff scales with project-creation frequency + multi-project conventions → more of a multi-project / team (Phase 2) feature than a solo-now feature.
