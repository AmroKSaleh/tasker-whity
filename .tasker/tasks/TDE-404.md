DELIVERED SCOPE (rewritten from the original "local-first architecture" framing — see below).

Goal that survived discussion: agents that have Tasker connected should reach for Tasker for DURABLE work instead of their platform-native to-do list (TodoWrite / Cursor todos). The native scratchpad KEEPS transient per-step execution ("read file X", "run the test"); Tasker OWNS durable work (real tasks, bugs found in passing, assigned work, tracked decisions).

What was built: rewrote the two instruction strings the MCP server already injects — no code/schema/tool changes, no user setup.
1. TASKER_SERVER_INSTRUCTIONS "YOUR NATIVE TASK LIST vs TASKER" paragraph (V2/supabase/functions/mcp/index.ts ~L560), returned in the initialize handshake so every client loads it before any tool call. Rewrote from PASSIVE ("don't mirror sub-steps") to ACTIVE routing ("is this DURABLE? → create_task, not your native list") with concrete durable-vs-transient examples.
2. New ASSISTANT_DIRECTIVES entry "DURABLE WORK BELONGS IN TASKER" (~L576), returned by __init_tasker_session, reinforcing the same rule for agents that read the full playbook.

Why this shape (not the original): the original task specified a local-first .tasker/board.json + sync daemon + conflict resolution + validation-lag rollback. Rejected because (a) the real pain is ADOPTION, not latency/tokens/offline — token bloat is already solved by context tiering, latency is fine, offline is hypothetical; (b) a hosted stateless Supabase edge function CANNOT watch a local file — the daemon model is architecturally impossible in this deployment; (c) making local files authoritative fights the positioning wedge (durable, human-shared, quality-gated state). Presence signals (CLAUDE.md snippet, SessionStart hook) were also rejected for THIS task — they leak per-repo/per-machine setup friction and undercut "by default"; the MCP instruction rewrite is zero-setup and cross-client (rides the MCP server the user already configured).

Honest limit: this is a strong behavioral DEFAULT, not a hard lock — an MCP server cannot disable a host's built-in TodoWrite.

Verification: deployed (supabase functions deploy mcp --no-verify-jwt); POST initialize to the live function returns result.instructions containing "ROUTE DURABLE WORK HERE, BY DEFAULT" and "is this DURABLE?" (HTTP 200, 2703-char instructions). Frozen as a kind=check review gate — PASSED.

FOLLOW-UP (deferred, gated on the CC plugin): when Tasker ships as a Claude Code plugin, bundle a SessionStart hook (plugins package hooks in hooks/hooks.json) that auto-inits Tasker + surfaces the ready queue — strongest CC engagement signal with zero incremental setup once the plugin exists. Still CC-only, so the instruction rewrite remains the portable floor for Cursor/Windsurf.
