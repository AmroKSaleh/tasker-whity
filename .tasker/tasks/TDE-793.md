Step 1 of the ground-up Flows definition (group: Flows — Definition from the ground up). THE ROOT question — everything else derives from this. Strip away all implementation (no contracts, edges, validators yet): what goes wrong when a person hands a multi-step piece of work to an agent using ONLY ordered tasks, that a 'flow' is meant to fix?

FORMAT for this + every step: (1) USER states what they WANT flows to be/do on this point; (2) we measure that against what flows CURRENTLY answer (137 design, playbook rule, TDE-320, TDE-212 evidence); (3) OUTPUT = a refined definition fragment for this dimension.

CONSTRAINTS (ground-up ≠ evidence-free): the definition must stay honest to TDE-212 (contract = proven win; independent validation = unproven) and must not throw away the working I/O-graph architecture — re-derive the CONCEPT, keep the plumbing.

OUTPUT: one crisp statement of the problem flows exist to solve.

--- Q1 OUTPUT (settled 2026-07-25) ---

THE PROBLEM FLOWS SOLVE (root):
A plain ordered list of tasks works until an operation gets LARGE. At scale, a single-context execution: (1) DRIFTS — loses fidelity over length; (2) SELF-APPROVES its own errors on unconsulted assumptions; (3) can't be safely INTERRUPTED and RESUMED (incl. across devices); (4) becomes an unreadable WALL of context for both human and AI. Flows exist to give a large multi-step operation a DURABLE, LEGIBLE STRUCTURE that keeps its quality, memory, and shape intact across its whole length — so bigness stops degrading it. The load-bearing word is SCALE: a Flow is what a task becomes when the operation is too big for one context to carry honestly.

The user's 8 wants are the 8 SYMPTOMS of bigness (not separate problems): #1 drift + #8 context-wall = two faces of the root (a monolithic context is WHY drift happens; separating context is HOW you fight it); #2 self-approval + #4 handoff-quality = quality rots at the joints; #5 = durability/resume; #3 = repeatability; #6 = human-executed step-by-step; #7 = legibility. All only bite AT SCALE — on a 3-step task none of them do.

MEASURED AGAINST WHAT FLOWS CURRENTLY ARE — THE GAP (important):
Current flows were built primarily as a QUALITY-GATING layer (contracts at seams + validators + revision loop — the whole 137 design). That is only ONE symptom (#2/#4). The current implementation does NOT directly serve the actual root:
- Context-separation to fight drift (#1/#8, the real root): NOT a deliberate mechanism today — each step is still a task with its own detail blob; decomposition helps only incidentally.
- Durability/resume across interruption + devices (#5): this is Local Mode's concern, not flows' — current flows have no special resume story.
- Human step-by-step execution (#6): Guide Mode exists but is minor, not central.
- Repeatability (#3): templates (152) exist but underbuilt.

CONSEQUENCE FOR THE DEFINITION: there is a gap between what the user WANTS flows to be (the answer to bigness) and what they currently ARE (a quality-gating layer — one symptom's solution promoted to the whole feature). The ground-up definition should consider RE-CENTERING flows from 'quality gates between steps' to 'durable, legible structure for big operations, of which gating is one benefit.' Carry this into Q2 (essence) and every later step.

--- Q2 BOUNDARY WORK (in progress 2026-07-25) — settled decisions so far ---

Q2 was RE-SCOPED: not 'write the one-sentence essence' (premature — a compression you can only do after the anatomy Q3-Q5), but 'draw the boundary: what's IN the flow concept and what's OUT.' The essence becomes Q2's OUTPUT, written last.

RESOLVED BOUNDARY (user decisions):
1. SCALE FLOOR (confirmed): a flow requires bigness. Test = the operation CANNOT be fairly held in ~2 tasks without becoming a wall of context. If it splits fairly into 2, it's by definition not big/complex/sensitive enough → not a flow. 2-step draft→review is NOT a flow.
2. OWNERSHIP: resume-across-devices is a HUB-level core capability that flows INHERIT (not owned by flows, not a Local-Mode-vs-flows question — remove from the flow boundary). Guide Mode IS a flow — the all-human-executor variant. → executor (human / AI / mixed) is an AXIS WITHIN flows.
3. CONNECTION IS NOT REQUIRED (the big one — user reversed an initial answer after catching a self-contradiction): a big SEQUENTIAL process is a flow too; steps do NOT need contracts between them. → SCALE is the essence; CONNECTION is optional; CONTRACTS/GATES are an OPTIONAL feature at seams, NOT the defining trait.

DEPARTURE FROM CURRENT IMPLEMENTATION (flag loudly): this contradicts the shipped definition. Today a flow = 'a connected component of the I/O graph' and the playbook says 'a flow with no contracts is just ordered tasks.' Under the new boundary, a flow is a BIG OPERATION GIVEN STRUCTURE whether or not it has contracts; the whole 137 contract/validator/revision layer DEMOTES from 'what flows ARE' to 'an optional add-on for the subset of flows with quality-sensitive handoffs.' This is coherent with Q1 (bigness = root, gating = one symptom) but means the current feature is built around the wrong center. 'Flow vs ordered-tasks-in-a-section' gets a NEW answer: the line is SCALE + intentional structure (treat as one durable, legible operation), NOT the presence of contracts.

RAZOR FOR TYPES (decided, feeds Q4 + Q6): 'sequential vs connected' does NOT merit two flow types — connection is a PER-SEAM attribute, not a per-flow property (the SAME flow has some hard-handoff seams and some merely-sequential seams; you can't type the whole flow by something that varies step-to-step). THE TYPE TEST: something is a real flow-TYPE only if it changes how the WHOLE operation is handled. By that test — executor (human/AI/mixed) PASSES (an all-human flow is run differently end-to-end); sequential-vs-connected FAILS (varies per seam). So: connection/seam-kind → belongs in Q4 (the seam). Graph SHAPE (linear vs DAG w/ fan-in) is a real property worth tracking (enables fan-in + auto-readiness) but is still NOT a type boundary — it's a property of the seam graph, not a species of flow.

STILL OPEN for Q2: write the final one-sentence essence (do LAST, after Q3-Q5 anatomy). Working shape: 'A flow is a large operation — too big to hold in ~2 tasks without a wall of context — given deliberate, durable, legible structure; bigness required, connection optional, gates optional.'
