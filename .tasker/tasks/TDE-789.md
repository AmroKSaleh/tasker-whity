DURABLE RECORD of the phase model settled in the 2026-07-25 strategy conversation that resolved seed TDE-788. Full canonical version lives in the phase_model memory; this task is the on-board record + the home for the remaining checklist work.

== THE PHASE MODEL (settled) ==
Sorting key: CORE = anything advantageous to the SINGLE user working alone. Multi-user/org/billing => Phase 2. Local-first => Phase 3.

PHASE 1 — Core app (hub + MCP), PRE-LAUNCH. Make the hub + MCP genuinely GREAT single-user tools. Scope IN: flows, I/O contracts, validation, Foundation/grounding, in-app AI, the inspector board, Drive file uploads, GitHub integration, environments (single-user only, no multi-user). Scope OUT: multi-user anything, Local Mode, going live.
  EXIT TRIGGER = LAUNCH. Going live IS the seam into Phase 2 (launch is an event, not a project). This REPLACES the old 'exit criteria = adoption metrics' framing — adoption metrics (DAU/MAU/churn) are POST-launch and cannot gate a boundary that IS launch.
  READINESS BAR = a capability checklist (specific conditions the tools must hit) CAPPED BY a test suite that publishes real numbers proving Tasker+features beat 'the AI as-is' (agent with no Tasker, native task tooling only). CRITICAL: the test must measure the axis Tasker WINS — durability across sessions, quality-gated output, handoff, drift over long projects — NOT single-session speed/tokens (the conceded lane where as-is wins).

PHASE 2 — Post-launch growth/business (project TPLB). Starts at go-live. Org/RBAC/teams/invitations/per-seat monetization/the 'human gate for other people' web-review surface. Built AS GitHub popularity creates demand, NOT pre-launch.

PHASE 3 — Local Mode v2 (project TLMV). The local-first fork.

== THE 4 CANDIDATE CRITERIA (from the original seed) NOW FEED THE CHECKLIST ==
These are the starting seeds for the Phase-1 capability checklist (to be drafted in full): (1) MOAT PROVEN — contract-gating beats ungated output (gated on the decisive contract-gating experiment); the likely hard blocker. (2) MOAT LEGIBLE TO HUMANS — a human can SEE gate/contract/judge state on the board. (3) TABLE-STAKES FLOOR CLEARED — search/filter/sort/board ergonomics not embarrassing (VERIFY current state, don't trust the stale architecture brief). (4) CORE WORKFLOW FEELS GREAT — the analysis→section→populate→direct-AI loop is smooth across MCP + web (TDE-343).
Decision model for the gate: MUST-HAVES + FOUNDER JUDGMENT (a couple hard blockers, the rest inform a final founder gut-check) — not pure all-must-be-true, not pure vibe.

== WHAT'S DONE vs STILL OPEN ==
DONE (this conversation): the phase MODEL, the exit trigger (launch), the sorting key, the TDE 3-way split (TDE→core, TPLB→business, TLMV→Local Mode), and the test-suite's measurement axis.

### CRITERION 1 — MOAT PROVEN
**Original bar:** contract-gating beats ungated output.
**Status: MET, but reshaped by the evidence — not a still-open blocker.**

TDE-791 Round 2 (done, 2026-07-30): B−A=+8.7pp, B−C=+0.87pp on a hard task, N=5/arm. Arithmetic this implies: C−A ≈ 7.8pp — contract/spec STRUCTURE alone beats ungated output by a wide margin — but adding an independent AI validator on top of that structure (B vs C) adds only ~0.87pp. The validator caught zero instances of an identical, checkable defect across all 5 B trials. This is the correlated-blind-spot hypothesis holding, not the moat failing: **the moat is durable, quality-gated STRUCTURE — not an AI judge catching what a human wouldn't.**

**Checkable bar, reshaped:** "Durable contract/structure demonstrably changes the failure mode vs. raw agent output" — MET by the ~7.8pp gap. Do NOT gate launch on "independent validation adds detectable value" — that's now a known negative result, already reflected in the Flows redefinition (Q5 demoted the AI judge to last resort).
**Classification: was a hard blocker, now closed.** The one live risk is MESSAGING, not engineering: any launch copy claiming the moat is "AI-judged quality" would overclaim what Round 2 actually showed. The defensible claim is contracts + human-gated exceptions, not AI-adjudicated correctness.

### CRITERION 2 — MOAT LEGIBLE TO HUMANS
**Original bar:** a human can SEE gate/contract/judge state on the board.
**Status: MET at the MCP layer, NOT YET at the web-board layer.**

get_flow_exceptions (TDE-382 promoted scope) shipped and was live-verified 2026-07-29: failed checks with observed evidence, judgment residue, terminal output, blast-radius ordering, suppressed passing checks. TDE-813 shipped honest Flows-UI badges (ungated flows visible, no false guarantees). But the actual web Flows page does not render get_flow_exceptions yet — that's TDE-816, and TDE-816 is blocked on the rebuild-or-refine decision.

**Checkable bar:** "A human looking at the Flows page — not an agent querying MCP — can see gate/exception state without opening every step." NOT YET MET.
**Classification: founder-judgment, not an automatic hard blocker.** Whether this gates launch depends on how much of the first cohort interacts via the web board vs. MCP-only. Worth an explicit call, not a default block — but it does mean **the rebuild-or-refine decision is now indirectly launch-relevant**, which it wasn't clearly framed as before.

### CRITERION 3 — TABLE-STAKES FLOOR
**Original bar:** search/filter/sort/board ergonomics not embarrassing. This milestone said "verify current state, don't trust the stale architecture brief" — done, and the state is genuinely split by surface.

**MCP side — advancing, shipped tonight (2026-07-31), NOT YET merged to main:**

- `list_kb_entries`: cursor pagination (was unbounded — this project alone has 84+ entries).
- `resolve_reference`: new tool, short-ID/UUID → entity type, live-verified.
- Global task search (TDE-314): done, pre-existing.

**Web-board side — real, unaddressed gaps, zero work done on either:**
- TDE-403 (show-all-tasks button + per-section sorting): completely untouched, no detail even written.
- TDE-263 (progress and priority filters can't be combined — only one active at a time): untouched, reads as a bug not a missing feature.

**Checkable bar:** "A first-time visitor using the web board hits no filter/sort behavior that reads as broken." NOT MET — TDE-263 specifically is the sharpest failure of this test; a filter that silently deactivates another isn't a rough edge, it's a bug.
**Classification: HARD BLOCKER for TDE-263 and TDE-403.** This is exactly the "embarrassing to a first-time visitor" test TDE-789 itself proposed, and TDE-263 fails it outright. Recommend both go on TDE-790's committed blocker list, not left in the general backlog.

### MILESTONE — the test suite (first draft, NOT a finished design)
TDE-791 Round 2 IS a working prototype of the methodology this milestone asks for (pre-registered arms, N≥5, a decisive verdict) — just scoped to one narrow question (does independent validation add value), not the full "Tasker beats the AI as-is" claim.

**Proposed generalization (sketch, needs its own design pass):** a long multi-session task, run twice — once with Tasker's durable state (KB, IS, task tracking, contracts) available, once with a bare agent using only native scratch/TODO memory — measuring drift, rework, and context-loss across N sessions. This targets the axis TDE-789 specifies (durability, drift over long projects) rather than the conceded single-session speed/token lane.
**This is a sketch, not a design — do not treat it as satisfying the milestone.** Recommend spinning it into its own task rather than finishing it inline here.
