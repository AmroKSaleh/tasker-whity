Outcome of the TDE-367 strategy discussion (2026-07-06). The "isn't Tasker too token-expensive?" objection is substantially TRUE of the current build and is now a top-tier product risk — because token economy is the hinge on which Tasker's whole cost-justification turns (durable state only beats re-deriving context if injecting it is cheap).

THE PROBLEM: every get_task call returns the FULL Project Foundation + the FULL Instruction Set + the ENTIRE KB index (61+ titles) — ~2–3k tokens of largely-repeated boilerplate the calling agent has usually already seen this session. get_project is worse. This inflates the cost of every single MCP interaction.

GOAL: tiered / lazy context injection. Ship the heavy context (Foundation, full IS, KB index) on session init or on explicit demand — not re-stamped onto every get_task. Mid-flow task fetches should carry only what that call needs.

Ideas to evaluate (not prescriptive):
- get_task returns task + a COMPACT header (project name, prefix, a 1-line pointer) by default; full Foundation/IS/KB index only via __init_tasker_session or an explicit include flag.
- Cache-awareness: don't resend context the agent received earlier in the same session.
- Summary/ceiling modes for get_project.

FOLDS IN TDE-319 (get_project overflows agent context on large projects — no size ceiling / summary mode) — that's one symptom of this broader issue; treat 319 as a sub-case and consider closing it into this task.

MEASURE IT: before/after token counts on a representative get_task and get_project so the win is verifiable, not asserted.

Full rationale in KB "Positioning: Tasker's wedge is durable, human-shared, quality-gated state (TDE-367)".
