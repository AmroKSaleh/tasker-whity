The SELF-CONTAINED TASK CONTEXT directive in __init_tasker_session tells the AI to write the detail field "so a cold reader can act" — but it doesn't draw the line between detail and milestones. In practice, the AI defaults to its documentation-writing instinct and dumps both context AND step-by-step actions into the detail field, leaving milestones unused.

What happened: a 22-task audit board was created for a WQW site audit. Every task had its action steps written as prose inside the detail field. The user had to explicitly ask for a second pass to move those steps into milestones. ~60 add_milestone calls were made after the fact to fix what should have been done at creation time.

The create_task tool already exposes a milestones array parameter — the AI just doesn't reach for it because no directive makes the separation explicit.

The fix needed: add one clear rule to the SELF-CONTAINED TASK CONTEXT directive (or as a standalone directive) stating the division of labor: detail = the why, background context, and any key decisions a cold reader needs; milestones = the ordered, checkable action steps. Steps do not belong in detail.

Removed the trailing "and the obvious next step" (which nudged prose-steps into detail) and added an explicit "DETAIL vs MILESTONES — DIVIDE THE LABOR" rule: detail = why/background/key decisions; milestones = the ordered checkable action steps, passed via the create_task `milestones` array (one per entry, never a checklist-in-note, no numbering — honors the Milestone Rule + No Numbering prefs). "Reach for the milestones array by default for multi-step work; steps-in-detail is the wrong default." Applies to all creation paths.
