EXTRACTED from TDE-556 on 2026-07-28. TDE-556 had merged this in (from TDE-557) as a "facet" of the query-surface engine, with the note "map coverage gaps against get_flow_audit / append_session_activity / get_task_activity first — this is consolidation, not net-new." That mapping has now been done and the premise was WRONG: the existing pieces do not cover it, and the dependency was inverted — you cannot query history that was never written. So this is a WRITE-PATH integrity fix that must land before any query surface over it means anything.

WHY THIS IS NOT A NICE-TO-HAVE: the canonical positioning line is "durable, human-shared, quality-gated state that persists across sessions, agents, and people." The gate history is the one part of that which is NOT durable. This is a hole under the load-bearing claim, not a mined competitor feature.

== EVIDENCE (verified in V2/supabase/functions/mcp/index.ts, 2026-07-28) ==
- get_flow_audit (index.ts:6148) is named "audit" but renders the CURRENT value of tasks.output.validation_ledgers. It is a snapshot renderer over mutable JSONB, not a log. This naming is likely why the gap went unnoticed in earlier assessments.
- confirm_contract (index.ts:8022) — the highest-trust human act in the system — writes only {confirmed, confirmed_at, confirmed_by} onto the live row. A later set_task_output (index.ts:6976) overwrites the contract wholesale and resets confirmed:false, ERASING that a human ever blessed it. No record survives that the confirmation existed.
- submit_task_review (index.ts:7157) overwrites review_verdict on every submission. Attempt 1's failures/critique are gone by attempt 2; only the `attempt` counter survives.
- submit_validation_result (index.ts:7631) writes output.validation_ledgers[edgeKey] keyed per EDGE, not per ATTEMPT. So retry_count (index.ts:7605) can report 3 gate failures while the content of all 3 is gone — which is exactly why get_flow_audit prints a retry count it cannot explain.
- enable_task_review (index.ts:7069) — the "frozen" bar is overwritten and lost when called with force:true. Frozen means frozen-until-someone-passes-force.
- disable_task_review (index.ts:7177) is the one handler written in the right spirit (leaves a superseding {cleared, reason, prior_overall} tombstone per the TDE-374 immutability comment) but it still overwrites the verdict it is tombstoning, preserving only prior_overall.
- Generic field changes (update_task, index.ts:4113) are lost on overwrite; only tasks.updated_at survives (trigger touch_tasks_updated_at), a timestamp with no indication of what changed. The transient changedFrom at index.ts:4116 exists only to populate a webhook payload and is discarded when no webhook matches (index.ts:113).

== SUBSTRATE (recommendation, decide before building) ==
agent_activities is the right substrate: append-only (UPDATE hard-blocked by trigger reject_agent_activity_update, migration 20260711120000_agent_session_ledger.sql:41), RLS'd, realtime-published, task-scoped. BUT: exactly ONE line in the 8,400-line MCP writes to it (index.ts:4900, the manual append_session_activity) — there is no logging helper at all. And its type CHECK constraint (progress/action/question/result/error) plus text-only `body` would need extending to carry structured {entity, field, before, after, actor} records. Grep confirmed NO table named *audit*/*history*/*event*/*changelog*/*revision* exists across all 68 migrations, and no DB-trigger history anywhere. The alternative is a new task_events table — note TDE-375's locked spec explicitly intended "write actor into ledger entries + a task-events log" and that log was never built, so this task completes that intent.

## SHIPPED + DEPLOYED — 2026-07-28 (branch tde-818-durable-gate-history, commit 519d244)

SUBSTRATE DECISION (milestone 1): **new `task_events` table**, NOT an extension of agent_activities. Reasons, so this is not re-opened: (a) agent_activities.session_id is NOT NULL, and a human confirming a contract in the web app has no agent session — synthesising one per human click corrupts what "session" means; (b) get_task_activity DERIVES session lifecycle from the LAST entry's type (index.ts ~4922-4928), so structural audit rows would become "last" and break it; (c) its type CHECK is narrative and body is text, while audit needs structured before/after JSONB.

DELIVERED:
- Migration 20260728120000_task_events.sql — append-only table (kind/entity/actor/summary/before/after/meta), `reject_task_event_update` trigger hard-blocking UPDATE, RLS mirroring agent_activities, realtime, partial index on meta.erased_confirmation.
- `recordTaskEvent` + `contractSnapshot` helpers. AWAITED rather than fire-and-forget (it is the audit record, not a notification) but never fails the mutation; drops go to mcp_error_logs so they are detectable, not silent.
- Recording wired into: set_task_output, derive_output_contract(apply), clear_task_output, confirm_contract (output AND input edges), enable_task_review, disable_task_review, submit_task_review, submit_validation_result, update_task.
- New `get_task_history` tool (filter by kind, verbose for full before/after, banner when a confirmation was destroyed).
- get_flow_audit header relabelled "Gate Snapshot" + points to get_task_history — it renders current mutable JSONB and its old name implied a log.

TWO FIXES BEYOND THE ORIGINAL SCOPE:
- set_task_output now WARNS the caller when it voids a human confirmation. That was previously entirely silent — you could unbless a human-approved bar with no signal.
- update_task fetched before-state via `if (k in task)` against a resolveTask result, but resolveTask selects a FIXED column list with no priority/due_date/pinned/executor/group_id/agent_ready — so an audit row could read "changed priority" with no prior priority. It now fetches the missing changed columns before the write (one indexed PK lookup, only when needed). Any other code deriving before-state from resolveTask has this same hole.

VERIFICATION (live, on a throwaway task, since deleted): 7 of 8 event kinds fired — contract_set, contract_confirmed, contract_cleared, review_bar_frozen, review_bar_cleared, review_submitted (×2), fields_changed. Proven specifically: confirm→overwrite preserves the destroyed blessing including confirmed_by/confirmed_at; two failing review attempts retain DISTINCT critiques (attempt 1 survives attempt 2); disable_task_review preserves the full bar + verdict it tombstones (previously only prior_overall). Frozen review bar + submit_task_review evidence recorded on this task.

TWO HONEST GAPS (not blockers, but do not claim otherwise):
- `validation_submitted` is code-complete but NOT live-fired — it needs a real flow with I/O edges. Verify opportunistically on the next flow run.
- The append-only UPDATE trigger was NOT empirically fired. Creation is confirmed (migration recorded applied remotely) but nothing exercised it: no MCP tool updates task_events, and the user/anon path is blocked by RLS before reaching the trigger.

HISTORY STARTS NOW. task_events records forward only — contract/review/gate changes made before 2026-07-28 were overwritten in place and are not reconstructible. get_task_history says so on tasks with no events.

## NEW GAP FOUND — logged as a follow-up, NOT fixed here
`fields_changed` fires only from the `update_task` handler. `complete_task`, `uncomplete_task`, `move_task`, `move_task_to_group` and friends write to `tasks` directly and produce NO history row — so a task being COMPLETED does not appear in its own gate history. Out of scope for TDE-818 (contract/gate/review surface) but worth deciding on if the log is meant to answer "what happened to this task?" generally. Recorded in the KB entry.
