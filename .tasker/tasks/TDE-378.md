From Linear: their MCP ships ~42 coarse tools and STILL gets publicly flamed as the biggest context hog in a 4-server stack (~12.8k tokens of tool definitions always loaded). Their countermeasures: merged create+update into one save_issue ("fewer calls, less latency"), changelog-level commitment to "reduced token usage through better tool documentation," a paste-any-URL resolver collapsing N lookup tools, Relay cursor pagination (default 50, has_more), and a uniform filter grammar incl. relative durations ("P2W") on every list endpoint.

Build: Tasker carries ~150 MCP tools — our most exposed flank. (a) tool census + token measurement of the loaded surface; (b) consolidation plan: merge create/update pairs (save_task etc.), audit every tool description as a token budget; (c) cursor pagination with small defaults + has_more on list_* tools; (d) small shared filter vocabulary (status/section/updated_since with relative durations) instead of ad-hoc params per tool; (e) a resolve-short-ID/URL tool collapsing lookups.

Direct extension of TDE-371 (context tiering) and the TDE-372 report — tiering fixed response size; this fixes REQUEST-SIDE surface. Token economy is now a public battleground; this is the enabling condition for the wedge (cheap injection).

## Item (d) DECIDED + SCOPE ABSORBED from TDE-556 — 2026-07-28

TDE-556 ("[STEAL] Query surface over the I/O + flow graph", mined from Azure DevOps WIQL) carried an open design question — **query DSL vs. param-object** — with "DECIDE before any build" attached. That question is the same decision as item (d) of this task ("small shared filter vocabulary … instead of ad-hoc params per tool"), approached from the opposite end: 556 came at it from CAPABILITY (let agents ask arbitrary questions across the I/O + flow graph), this task comes at it from TOKEN ECONOMY. One decision, so it is settled here and 556's engine scope folds in.

**DECISION: param-object, i.e. THIS task's shared filter grammar. Not a DSL.** Rationale:
- A DSL has to be *taught* in a tool description — the exact flank this task identifies as our most exposed. Measured 2026-07-28: the MCP ships **137 tools, 34 of them list_*/get_***.
- Agents emit malformed novel DSLs and burn retries; they get JSON filter objects right first try.
- The strategic inversion, and the reason this is worth doing: as a shared params grammar, ONE query tool can **subsume** several of those 34 read tools — the query surface becomes this task's *enabler* rather than tool #138. As a DSL it is a parallel access path duplicating tools that already exist, and it makes the token flank worse.

**What folding 556 in adds to item (d):** the grammar must be able to express relationships, not just scalar field filters — I/O edges, flow membership, contract/gate state, review state. The motivating query shape from 556 was "all tasks whose output feeds an unfinished task in section X", which a flat status/section/updated_since vocabulary cannot express. Design item (d) to cover that class of question, not just the easy filters.

**Sequencing constraint:** querying gate/contract/review HISTORY depends on TDE-818 (Durable gate history) landing first — that state is currently overwritten rather than recorded, so there is no history to query yet. Current-state relationship queries (edges, flow membership, current gate state) have no such dependency and can proceed independently.

Downstream: TDE-556 is now reduced to the thin human-facing saved-views wrapper over whatever grammar this task ships (one engine, two faces).

**Milestone 3 (resolve_reference) — CODE DONE, DEPLOYED, SCHEMA-VERIFIED. Behaviorally UNVERIFIED — leaving unchecked.** New tool: given a bare short ID or UUID with no prior knowledge of its type, identifies task ("TDE-52") / flow ("TDE-F1") / project ("TDE") and returns identity + a "next" hint. Real finding while building it: **no other tool could look up a flow by its own displayed short_id** — every flow_id param only matched a UUID or a name substring (`ilike`), so a flow's own visible identifier was unusable as input anywhere. resolve_reference is the first fix for that.

**Milestone 2 (pagination + filter grammar) — MECHANISM DONE, VERIFIED LIVE, but wired to only 2 of ~34 list_*/get_* tools — leaving unchecked, not a full "on list_* tools" claim.**
Built as reusable helpers (encodeCursor/decodeCursor/applyCursor/clampLimit near the top of index.ts): keyset pagination on (sortCol, id), not OFFSET — stays stable while rows are edited between pages, unlike offset pagination. Wired into:
- `list_tasks`: sort_order or updated_at as the keyset column, limit (default 50/max 200), cursor.
- `list_kb_entries`: created_at as the keyset column, same limit/cursor.
Shared filter grammar (item d, already decided as param-object not DSL): `updated_since` on list_tasks — relative durations ("7d"/"2w"/"1mo") or ISO-8601 ("P2W") or an absolute date, via the new resolveSince/parseRelativeDuration helpers.
`blocking` on list_tasks — TDE-556's fold-in, the first relationship filter: only tasks whose output is an input source (per the existing I/O-edge model, `inputSourceIds`) for at least one NOT-done task anywhere in the project. **Architectural constraint, by necessity not oversight: this is computed in JS by fetching the project's task/input/status rows and building a reverse index — a JSONB reverse-lookup isn't a single indexed WHERE clause — so `blocking` DISABLES cursor pagination for that call (returns the full filtered set) and requires project_id.** Both are stated in the tool description, not left implicit.

VERIFIED LIVE (not just typechecked):
- Cursor pagination: two consecutive list_tasks(limit:5) pages confirmed to continue without duplicating or skipping rows.
- updated_since:"2d" correctly bounded a recently_updated, status:"all" query to the last 2 days.
- blocking: built a throwaway producer/consumer pair (deleted after), wired via set_task_input. Producer appeared under blocking:true while the consumer was open; disappeared once the producer itself completed (a done producer isn't a bottleneck) under the default status filter; reappeared correctly under status:"all". Also surfaced an EXISTING, unrelated mechanism while testing: complete_task on a consumer is hard-blocked while its upstream producer isn't done — "Dependencies are enforced — there is no override," confirming the I/O-edge model has real teeth elsewhere in the codebase already.
- deno check: introduced one new error class mid-draft (TS18047, 'data' possibly null) from typing an accumulator as `any[] | null` — fixed by typing it `any[]` instead of suppressing. Final count: 32, matching the pre-existing baseline exactly.

REMAINING FOR MILESTONE 2, sized: extending the same encodeCursor/decodeCursor/applyCursor pattern to other unbounded list_* tools (get_task_history, list_flows, get_flow_audit are the next candidates by row-count) is now mechanical repetition, not new design — the pattern is proven. Relationship-query coverage beyond `blocking` (flow membership, contract/gate state per TDE-556's full fold-in) is NOT started; querying gate/review HISTORY specifically depends on TDE-818, which is already shipped, so nothing blocks starting that whenever it's picked up.
