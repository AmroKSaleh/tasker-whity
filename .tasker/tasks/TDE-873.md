**The ask (user's words):**

"Make the project updates a tool/method that can be used by the user to give the LLM the complete context that is needed to resume the work from the point it stopped the last session. This requires the MCP to have the ability to read the project updates/history."

**Why — the concrete failure that produced this task.**

This came out of a live session on the WQW (Waqtak Website) project on 2026-08-06. The sequence:

1. The user asked for a project update. The agent called `get_project_delta(WQW)` and it returned all zeros — 0 completed, 0 added, 0 blocked — on a project with 100+ tasks and multiple active workstreams. Delta is computed since the last *published* update, so an active project can legitimately show nothing.
2. Because delta was empty, the agent had to reconstruct the project's standing position by calling `get_project` and reading the entire board — every section, every task, every status — then writing the narrative by hand. That is an expensive, high-token orientation pass, and it is exactly the pass a resuming agent has to repeat every session.
3. The agent posted the draft via `post_project_update`.
4. The user then said: "read the last draft update, so we can continue working from there." **This was impossible.** There is no read tool. The agent could only answer because it had authored the update itself minutes earlier and still had the text in its own context window. In any later session, that update would have been unreachable.

**The core defect.** Project updates are currently write-only from the MCP surface: `post_project_update` (write) and `get_project_delta` (compute inputs). Nothing reads them back. So the artifact best suited to be a session-resume handoff — a human-blessed, health-rated narrative of where the work stands — can be authored by an agent and then never consumed by one. That is backwards from its highest-value use.

**What the feature should become.** The published project update becomes the cheap, high-signal orientation artifact: a resuming agent reads the last update instead of dumping the whole board. It is better than a raw board dump because a human has reviewed and blessed it, it carries a health judgment, and it states what should happen next rather than just what exists.

**Design notes and open questions (decide these, don't assume):**

- *Drafts or published only?* The user's request explicitly said "read the last draft update," so drafts appear to be in scope. But a draft is unreviewed — feeding an unblessed draft to an agent as authoritative resume context has a different trust profile than a published one. Recommend readable but clearly labelled with draft status, and let the caller filter.
- *Pull or push?* A read tool the agent must remember to call will often not be called. Consider surfacing the latest published update automatically — alongside the Foundation in `get_project_foundation`, or in the `__init_tasker_session` / `get_my_attention` payload — so orientation happens without the agent knowing to ask.
- *Delta cannot be the payload.* The WQW case proves an update authored purely from delta can be empty on a genuinely active project. The narrative body is doing the real work; delta is a supplement. Whatever "resume context" shape is chosen must not assume delta is populated.
- *What does a resuming agent actually need?* Probably: current health, the narrative body, what moved, what is blocked and why, and an explicit "next action" pointer. Worth defining this as a structured shape rather than leaving it entirely to free prose — the WQW draft had to invent its own structure.

**Relevant existing surface:** `post_project_update`, `get_project_delta`, `get_project_foundation`, `__init_tasker_session`.

## CONFIRMED 2026-08-06 — the gap is total, not draft-specific. And updates may not be in the export either.

Re-checked the MCP surface with a second, differently-worded search after the user asked whether a PUBLISHED update (as opposed to a draft) can be read. It cannot. The distinction makes no difference.

The complete set of update-related tools is two:

    post_project_update    writes a DRAFT (health + body); server attaches the delta
    get_project_delta      computes tasks completed/added/blocked since the last PUBLISHED update

Nothing returns an update's health, body, author or timestamp, in any state. So the read gap is not "drafts are not exposed", it is "updates are write-only, full stop". Any read tool built for this should cover both states from the start; the draft-versus-published question is only about what to RETURN and how to label it, not about whether reading is possible.

### SEPARATE GAP NOTICED WHILE CHECKING: updates are likely absent from export_project

export_project describes itself as producing a "portable, full-fidelity JSON bundle" and enumerates its contents: Foundation/context, sections, groups, tasks (milestones, I/O edges and contracts, flow membership, custom statuses), flows plus flow IS/KB, the project KB and the IS. It states that ephemeral state (drafts, intake jobs) is excluded. Project updates are not named anywhere in that list.

If that enumeration is accurate, a project's entire published update history is not in its own backup, and would be lost on an export/import migration. That is a data-durability problem independent of the read-tool question, and it should be verified against the actual export payload rather than taken from the description alone.

Worth folding into this task's scope: whatever shape "readable update history" takes, it should also be exportable, or the feature builds a resume-context artefact that cannot survive a project move.

## THE DELTA COUNTS ARE TRUE AND STILL MISLEAD — found by reading a real update, 2026-08-06

The 2026-08-06 draft update rendered "20 Added / 10 Completed / 0 Blocked". Owner's reaction, verbatim and worth keeping as the clearest statement of the defect:

> "What I understood from these numbers is that between this update and the last we added 20 tasks to the project, and that we completed 10 tasks. It doesn't show if the 10 tasks are from the added 20 or not, which made me assume that the 2 statistics are independent."

That is the natural reading and it is wrong. Two counts presented side by side with no stated relationship default to being read as disjoint sets. Here they overlap by 80%.

**The actual figures for that window (since 2026-08-01T20:20:01Z):**
- 20 added, 10 completed
- 8 of the 10 completed were among the 20 added
- only 2 completions were tasks that pre-existed the window
- net change to the open backlog: +10, not +20

**Why this is not cosmetic.** The independent reading says "the backlog is being worked down while new work arrives." The true reading says "nearly all completion went to work discovered inside this window; the standing backlog moved by two." Those are different stories about the project, and a reader judging backlog health takes away the opposite of what happened.

**What the fix must NOT be.** Simply reporting "8 of 10 completions were same-window" is better but still cannot distinguish the two cases that produce identical numbers:
- sweeping for launch blockers and closing what you find — the system working as intended, which is what 2026-08-06 actually was
- getting pulled onto whatever is loudest while the real backlog rots — the same shape, and a problem

The counts cannot tell these apart. Consider whether the update should carry the intent (a deliberate sweep vs. reactive churn) rather than leaving the reader to guess, since "new work jumped the queue" is only meaningful with the reason attached.

**Three further distortions observed in the same real window:**
1. **Duplicates inflate both counts.** TDE-874 was filed as a duplicate of TDE-870 and merged. It counts as +1 added and +1 completed while representing no work at all.
2. **Not-a-defect closures count as fixes.** TDE-867 was closed with zero code changed — the reported bug did not exist. TDE-864's central premise was also false; two hand-typed rows, no write-path bug. Roughly three of the ten "completions" were corrections to the BOARD rather than changes to the product.
3. **Discovery is invisible as an output.** Five of the six launch blockers closed on 2026-08-06 did not exist a week earlier. They were found by sweeping the app and by measuring token spend, not selected from a backlog. Finding them was the substantive work, and the update format has no way to show it — it renders as churn.

Point 3 connects to the pattern recorded on TDE-790: four filed diagnoses this session were wrong or stale on contact. If a meaningful share of completions are the board correcting itself, that deserves its own signal — it distinguishes a team shipping from a team discovering its records had drifted.

SUGGESTED DIRECTION (not yet decided): report net open-backlog change as the headline rather than two raw counts; split "added" into still-open vs. closed-same-window; exclude merged duplicates; and consider a distinct marker for closures that changed no code.
