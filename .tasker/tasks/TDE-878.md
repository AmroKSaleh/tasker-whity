Found 2026-08-06 while fixing TDE-870. Not a bug in the filter — a gap between when the feature shipped and when the data was written.

THE MECHANISM WORKS. get_task filters Instruction Set entries by tags at supabase/functions/mcp/index.ts (the `applies` helper, shipped as TDE-782). An entry is included if it has no tags, or if its tags intersect the task's tags. That rule is right: untagged must mean applies-to-everything, or adding the feature would have silently stripped governance from every existing project.

THE GAP. Tags landed 2026-07-31 (migration 20260731175700_add_tags_to_tasks_and_is.sql). Every Instruction Set entry written before that date is untagged, therefore matches everything, therefore the filter is a no-op on real projects. Verified on WQW: all five entries date from May/June 2026 and none carry tags.

CONCRETE COST. WQW's IS is ~2,500 tokens, of which ~1,800 is a single "Article release flow is mandatory" entry. TDE-870 measured eight task reads in one session — seven were security, caching or DNS work, and every one received the article publishing procedure. After the TDE-870 fix that is once per project per session rather than once per call, so the impact is much smaller than it was, but it is still paid on the first read of every session and it scales with IS richness.

WHY THIS IS NOT JUST "GO TAG THEM". Nothing surfaces the cost or prompts the tagging. A user who enriches their Instruction Set is penalised for it and never told why, and the feature that would fix it is invisible unless you already know it exists. Decide whether the answer is a nudge, a report, a backfill prompt during some existing flow, or simply documenting it.

OPEN QUESTION worth settling first: should an untagged entry keep meaning "applies to everything" forever? The alternative — untagged means universal only for entries created before the cutoff, and new untagged entries warn — preserves the safe default without freezing the gap permanently.
