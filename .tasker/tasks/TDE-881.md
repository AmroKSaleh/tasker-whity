Build task for Finding 1 of TDE-372 (Measurement 2, 2026-08-07). TDE-372 stays reference-only — it holds the report; this task holds the work.

## The problem

ASSISTANT_DIRECTIVES (supabase/functions/mcp/index.ts:1665-1688) is a flat array of 22 strings, ~21,000 chars, shipped WHOLESALE on every session at two call sites: index.ts:6774 (returning user) and index.ts:6838 (questionnaire path). Measured ~6,000 tokens, ~74% of the cost of a cold session's first request. On a sampled read-only request ("list the tasks in Core App") zero directives applied.

The cost is NOT dollars — it lands in the cached prefix, ~10% of input price after turn one, and ~$0 on the owner's subscription. The costs that matter: (a) ATTENTION — every irrelevant directive is a rule the agent must decide not to follow, and instruction-following degrades as the pile grows; (b) third-party users on metered API clients pay it per session.

Do NOT solve this by cutting or shortening directives for their own sake. They are load-bearing — the flow definition exists because agents were inventing their own, which costs far more to clean up than 6k tokens. The fix is to make the charge CONDITIONAL, not smaller.

## The load-bearing design constraint (found while scoping, changes the naive plan)

Directives split into two kinds, and only one is safely deferrable:

- PROCEDURE directives tell the agent HOW to do something once it has already reached for the tool. These can be lazily injected into that tool's response — by the time the agent needs them, it has called the tool. Safe to defer.
- TRIGGER directives tell the agent WHEN to reach for a tool it would not otherwise call. These CANNOT be lazily loaded on that tool's response: if the agent never learns the trigger, it never calls the tool, so the injection never fires. Deferring a trigger silently kills the behavior.

The resolution: keep a COMPRESSED one-line stub for every trigger in the always-on core, and let the stub point at the tool that carries the full procedure. This works because several tools ALREADY return their own playbook — bootstrap_project returns its phases, build_new_flow returns a playbook + project grounding (see the comment at index.ts:8233), run_flow returns the run playbook. For those, the directive text is partly DUPLICATING what the tool already ships, so deferring costs nothing.

## Proposed split (~1,500 always-on vs ~4,500 deferred)

ALWAYS-ON CORE (~1,250-1,500 tokens): attention-first; durable-work routing; task lifecycle (in_progress / complete); dedupe-before-create; ambiguity + bias-to-action; no-sycophancy; self-contained task context (detail vs milestones); verify-before-complete. Plus new one-line TRIGGER STUBS for: flows ("multi-step operation too big for one sitting -> call build_new_flow, it returns the full definition and interview playbook"), autonomous loop ("user says 'start looping' -> call get_ready_work, it returns the loop playbook"), relay ("user wants to hand a task to someone -> see relay_context"), bootstrap ("new project -> call bootstrap_project FIRST").

DEFERRED BUNDLES, injected once per session on first touch of their trigger tool:
- flows (~2,450): FLOW vs AD-HOC full definition, build/run/name, NEVER-ASK-HUMAN-TO-REVIEW, step-list-open, revision loop, validation independence, check-rule execution. Trigger tools: build_new_flow, run_flow, validate_output, submit_validation_result, get_flow_context, get_flow_exceptions, store_artifact.
- local-mode (~630): the pull/ground/work/flush bracket. Trigger: pull_local_project / flush_local_project / set_local_mode — and the server ALREADY knows whether a project has Local Mode on, so it can inject on any project-scoped call instead of relying on the agent.
- autonomous-loop (~420): trigger get_ready_work.
- relay (~290): trigger create_task/update_task carrying relay_context.
- bootstrap (~240): trigger bootstrap_project.

## Mechanism

Reuse the TDE-371 pattern rather than inventing one. mcp_context_primed already tracks per-session priming per user and is wiped on __init_tasker_session (index.ts:6740), which is exactly the session boundary needed. Add a bundle key so a bundle is injected once per session, then suppressed.

Rejected alternative: a get_directives(bundle) tool. It depends on the agent taking initiative to call it, and the core list would have to spend tokens explaining when — reintroducing the cost it was meant to remove. Server-driven injection needs zero agent behavior change.

## Watch-outs

- Two call sites must both change (6774 and 6838) — the questionnaire path is easy to miss.
- The MCP is a shared edge function; a bad split degrades EVERY session and every third-party user, not just the owner's. Verify against a cold session before considering it done.
- TDE-870 (RLS on mcp_context_primed) is the precedent for the failure mode here: a silently-denied write latched context suppression on permanently. Any new priming key must be checked for the same RLS trap.
