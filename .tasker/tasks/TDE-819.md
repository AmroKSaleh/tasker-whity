FOLLOW-UP TO TDE-818 (which shipped the task_events log). Found while verifying that work: `fields_changed` fires ONLY from the `update_task` handler. Every other handler that mutates task lifecycle state writes to `tasks` directly and produces NO history row — so a task being COMPLETED does not appear in its own gate history, which makes get_task_history misleading for the most basic question a reader asks ("what happened to this task?").

Verified by grepping every `from('tasks').update(` call site in V2/supabase/functions/mcp/index.ts.

== IN SCOPE — 9 sites, all task-lifecycle (status / location / closure) ==
- complete_task (index.ts:4258) — status → done
- uncomplete_task (index.ts:4290) — status → pending
- move_task_to_group (index.ts:6040) — group + optional section change
- move_task (index.ts:6091) — cross-project move; rewrites project_id, section_id, group_id, flow_id, flow_step and drops all input edges
- set_task_phase (index.ts:3912 unphase / 3918 set) — phase change
- merge_task_as_duplicate (index.ts:4081) — closes the dup as MERGED (duplicate_of set), a distinct outcome from plain done
- resolve_seed (index.ts:4133) — closes the seed
- get_task auto-start (index.ts:4355) — status pending → in_progress. DECIDED 2026-07-28 (user): RECORD IT. It is the same class, it is bounded (fires only when status is pending), and it is precisely what caused trouble in this session — a read-only survey silently flipped 8 tasks to in_progress and they had to be detected and reverted by hand. Logged, that becomes visible.
- advance_guide (index.ts:6939) — completes a guide step

Implementation: reuse kind='fields_changed' + entity='task' with `meta.via` naming the handler. Deliberately NOT a new event kind, because the kind CHECK constraint in migration 20260728120000 would need altering — `via` carries the distinction at zero migration cost.

== DELIBERATELY OUT OF SCOPE (do not silently expand) ==
- flow_step renumbering (7105, 8158, 8210, 8478) — internal ordering bookkeeping, not lifecycle
- input/output edge + contract writes (7076, 7131, 7421, 7433, 8315, 8466) — already covered by the contract_* event kinds
- store_artifact (7561), drive_files (5688) — artifact storage, not gate state
- delete_flow unlinking (7470), delete_group ungrouping (981, 6019) — bulk teardown side-effects
- submit_validation_result reopening the producer (7824) — already contextualised by its validation_submitted row
- import/instantiate bulk creation (3278)

== KNOWN REMAINING HOLE AFTER THIS (separate decision) ==
The Local Mode flush path (index.ts:1121) writes task fields directly from .tasker/ files. File-driven edits will still not appear in gate history. Different semantics (bulk reconciliation, LWW, hub_wins corrections) so recording there risks double-counting — needs its own think, not a copy of this fix.

KB: "Architecture: task_events — the append-only gate-history log (TDE-818 shipped)" documents the gap this closes.
