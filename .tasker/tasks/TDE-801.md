Step 9. Is a flow a one-off or a reusable process? Current answer: the three-layer split — Process (fixed) / Contract (mostly fixed, the reusable IP) / Context (per-run subject). Contracts must be context-free/portable so templates are near-free (152). Do you want flows to be templatable, and is the process/contract/context split the right seam for fixed-vs-varying? OUTPUT = the reuse/template definition.

---

## OUTPUT — reuse: the bar is the reusable unit (settled 2026-07-28)

### The reusable unit is the BAR, not the SHAPE
`save_flow_as_template` / `instantiate_flow_template` currently copy the **shape**: steps, order, I/O wiring. That is the cheap half. An agent can propose "research → draft → edit → publish" for a new subject in seconds; nothing valuable was lost by not saving it.

What actually cost something is the **bar** — the criteria the human and AI worked out about what good looks like at each seam (the word-count floor, "every claim carries a source", the tone rule, the thing only discovered on the third run). Per Q7 that is where the human's attention is spent, once. A template carrying only the step list copies the wrong payload.

Bars are also more **portable**: "every claim has a source" applies across many different flows; a five-step shape applies to one kind of work. Higher reuse density.

**Precedent in the product:** default Instruction Sets, baseline-seeded onto every new project (TDE-295) — human judgment captured once, applied automatically thereafter. A reusable bar is the same mechanic at SEAM level rather than project level. This suggests the answer looks more like a **criteria library** than like flow templates.

**Fair counter, accepted:** for genuinely repeated operations (the same weekly report, the same onboarding run) the shape IS stable and copying it saves real setup. So shape-reuse survives — narrower than the current feature implies, and kept SEPARATE from bar-reuse.

### The mechanism (user's design, adopted)
A manual **"update Flow template"** button. After a run, the user is shown what the run would change in the base template, with the effects of each change, and commits or omits them selectively.

**Manual is REQUIRED, not merely cautious.** Q8 settled that the agent decides WITHIN the bar and never ABOUT it. Automatic template promotion would be the agent quietly rewriting the standard from one run — the move that would make the contract layer decorative. The button is the correct mechanism.

The diff-with-selective-commit shape is also Q7's exception review applied to templates: don't show everything, show what changed and let the human rule on it.

### Three refinements on top of the user's design
**Event-source the findings; do not diff at the end.** The highest-signal moments happen MID-run — the instant a criterion is edited, a gate overridden, a rule added. Log each as an event with its context when it occurs, then present the accumulated list at the end for the commit decision. An end-of-run diff must reconstruct intent from before/after state, and the WHY is exactly what is lost.

**The most valuable finding is a MISSING rule.** When a human rejects an output at a gate where every check PASSED, no rule failed but something was wrong. That is a detectable **rule-gap event**, it is the same signal Q5 named ("met the bar, still unusable → the bar was wrong"), and it should feed the template as a PROPOSED NEW CRITERION. Worth more than any edit to an existing rule.

**Split the diff into SHAPE changes and BAR changes.** Steps added/removed/reordered mid-run are usually one-off adaptations to that subject; criteria changes usually generalise. Presented together, the human approves shape drift they did not mean to keep.

### Constraint
A template update must NOT alter runs already in flight. **Instances are snapshots at instantiation; the template is versioned behind them.**

### Consequence to carry into Q11
This makes a template sharpen every time it is run — quality standards COMPOUND instead of being re-derived per subject. That only works because the durable state exists to accumulate into, so it is a moat-shaped property, not a convenience feature.
