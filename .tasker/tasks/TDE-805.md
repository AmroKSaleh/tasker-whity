IDEA (user, 2026-07-26): a dynamic KB that lives at the USER level rather than inside a project — a store of the user's own knowledge and books. It gets its own place in Tasker: its own page and its own navigation entry. Entries held there can then be USED INSIDE a project.

WHY THIS IS NOT WHAT WE ALREADY HAVE
Today every KB is scoped to a container — project KB (per-project), plus flow-level KB. There is no user-level library. The closest existing thing is personal/org DEFAULT Instruction Sets + user-defined default ISs/KBs, which SEED a new project at creation — a one-time COPY. This idea is different in kind: a standing library that projects REFERENCE. That distinction is the core design decision (see open questions).

THE TWO OPEN QUESTIONS THAT DECIDE THE SHAPE

1. REFERENCE vs COPY. When a library entry is "used inside a project", is it linked (one source of truth; editing the library updates every project using it; deleting/changing it can silently move ground under a project) or copied in (project stays stable and self-contained, but the copies drift from the library and from each other)? Everything else — sync behaviour, deletion rules, whether a project can locally override an entry — follows from this. Reference is the more useful answer and the more dangerous one; a hybrid (link by default, "detach to edit locally") is worth considering.

2. BOOKS ARE NOT KB ENTRIES. This is the load-bearing risk. The existing KB is built around SHORT DISTILLED LEARNINGS: a titles-only index is injected into agent context, and the agent selectively pulls the few entries it needs. That design assumes entries are small. A book is a large document — it cannot be pulled whole into context, and a titles index of books tells an agent almost nothing about what is inside them. Storing books in the KB as-is would either blow the token budget or be dead weight the agent never retrieves from. Books plausibly need a different retrieval path than KB entries (chunking/extraction/search rather than whole-entry pull), even if they share a page. Decide whether "knowledge" and "books" are ONE entity with two sizes or TWO entities sharing a home — do not assume the former by default.

OTHER THINGS TO SETTLE
- Scope boundary: is the library per-USER, or does it also need an ORG-level tier (the org layer + Environments already exist, and a shared team library is the obvious next ask)? Environments partition projects — decide whether the library is global across Environments or scoped per Environment.
- MCP surface: agents are the primary consumer. Needs list/get tools for the library, and a way for the agent to know a library entry is in play for the current project without re-shipping it on every call (the get_task context-tiering work is the precedent to follow — do not regress the token economy).
- Retrieval quality: the project KB already has a category soft-hint and a titles index for selective pull. A library that is larger and less project-specific makes precision harder, not easier. Whatever retrieval story exists must get BETTER, not just bigger.
- Interaction with existing adjacent work: @-references/typed links between tasks and KB entries; the KB-vs-embedded-docs-editor evaluation; the existing archive/staleness sweep (does a library entry go stale the same way a project entry does?).

STATUS: an idea to be designed, not a specified build. First move is a design pass answering the two questions above, not writing code.

### Why this is not a duplicate of what exists
The nearest existing thing is user-defined default Instruction Sets / KBs, which seed a new project at creation. That is a one-time COPY at birth. This idea is a STANDING library that projects draw on — a different feature, not a variation of that one. The duplicate check flagged the old per-project KB task at 55%, which is not a match.

### The agent's concern about books (recorded, not settled)
The existing KB is built for short distilled learnings: a titles-only index goes into agent context, and the agent pulls the two or three entries it needs. That design assumes small entries. A book appeared to break both halves — it cannot be pulled whole into context, and a title alone tells an agent little about the contents. The agent's read was that books would therefore need a different retrieval path (search or extraction rather than whole-entry pull), even if they share a page with knowledge entries, and that assuming "book = big KB entry" would produce a library the AI never actually retrieves from.

### The agent's concern about reference vs copy (recorded, not settled)
Linking gives one source of truth but means editing the library changes the ground under every project using it; copying keeps projects stable but lets copies drift. Sync behaviour, deletion rules, and local-override behaviour all follow from that choice. A link-by-default with detach-to-edit hybrid was floated as worth considering.

### The agent's note on scope tier (recorded, not settled)
The org layer and Environments already exist, so a shared team library is a plausible near-term ask. The agent's view was that deciding the scope tier up front is cheaper than retrofitting one later. Whether that matters depends on the user's intent for the feature.

### What still stands regardless of the above
Whatever shape this takes, it must not regress the MCP context/token economy — the get_task context-tiering work is the precedent. And retrieval precision has to get BETTER as the corpus grows, not just bigger; a larger, less project-specific store makes precision harder by default.
