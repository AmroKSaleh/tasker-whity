The half of local structural ops that CANNOT use the slug-is-name / create-by-reference trick: renaming, deleting, and reordering groups and sections through files. Split out from the "add group/section/milestone functionality" push (2026-07-18) because create + milestones were cheap (shipped separately) but this needs a NEW writable file + a real design decision — it reopens the "Option 2 manifest" space deliberately parked during TDE-581.

WHY create-by-reference can't cover rename: a group's/section's IDENTITY in files is its SLUG, and the slug derives from the NAME. Rename the name → the slug changes → every task's `group:`/`section:` reference points at the OLD slug and orphans. So rename needs a STABLE identity that a name-derived slug can't give. Same for delete (need to express "this group is gone" — absence is ambiguous vs. "no task references it right now") and reorder (needs an editable order, but project.json is a read-only regenerated snapshot that flush ignores).

LIKELY DIRECTION (decide during resolution): a writable groups/sections MANIFEST file in .tasker/ that flush DOES apply (unlike project.json). Each group/section is a stable line (stable id/slug + editable name + order + section-parent). Rename = change the name on its line (slug/id stays). Delete = remove the line (tasks fall to ungrouped / section handling TBD). Reorder = change order. This is the "Option 2" from TDE-581.

OPEN QUESTIONS to settle before building:
- Manifest format: extend project.json to be writable-for-these-fields, or a dedicated groups.md/sections.md? (project.json is currently read-only carriage; making part of it writable vs. a new file is the core fork.)
- Stable identity: keep the current name-derived slug but add an explicit stable id column? Or freeze slugs at creation so rename doesn't move them?
- Delete semantics: manifest-line-absence = delete? What happens to a non-empty group/section on delete (tasks → ungrouped? refuse if non-empty?).
- LWW / conflict rule for STRUCTURAL ops across devices (two devices rename/add groups concurrently) — needs its own rule like task LWW. This was open question #4 on TDE-581.
- Section delete is higher-stakes than group delete (a section holds groups+tasks) — maybe delete stays MCP-only even here?

POINTERS: applyFlush + resolveGroupForTask (create-by-reference) in index.ts; slug logic in sync_core.ts (slugify/buildSlugMap/buildPullMaps); serializer local_format.ts (serializeProjectJson is the read-only snapshot today). KB: "Local Mode: group create-by-reference via flush (TDE-581, slug-is-name)" explains why slug-is-name works for create but not rename. Umbrella TDE-534.
