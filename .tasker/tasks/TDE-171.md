RESOLVED (2026-06-10) — dependencies are now hard-enforced server-side.

Root cause: enforcement was advisory + 1-hop. update_task/complete_task returned a flow_blocked dialog only when !proceed_anyway, and the agent could set proceed_anyway:true to blow through it; get_task auto-start surfaced a warning but pointed the agent at the same proceed_anyway override. unmetSources only checked DIRECT parents (1-hop), so deeper chain gaps weren't caught.

Decision (owner, via options): HARD BLOCK, no self-override.

Fix (V2/supabase/functions/mcp/index.ts):
- New unmetSourcesDeep(): walks the WHOLE upstream chain (transitive), cycle-safe via a seen set, recurses only past not-done sources (a done source means its own upstream is already satisfied).
- update_task (in_progress/done) and complete_task: now hard-block on any unmet upstream — the proceed_anyway bypass is gone for the dependency gate (still used only for the separate artifact-missing check in complete_task). Returns flowHardBlockedResponse (enforced:true, no override option).
- get_task: blocked tasks stay pending with a new ⛔ message stating enforcement + no override.
- Removed dead unmetSources / flowBlockedResponse.

To work out of order now: finish/reorder the upstream, or remove the edge via set_task_input.

Verified live (3-task chain A→B→C in BPW): start C with both pending → blocked listing B+A (transitive); complete A → C now blocks on B only (recursion stops at done); complete B → C starts. Deployed to Supabase.
