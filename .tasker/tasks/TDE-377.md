From Linear: per-model webhooks with payload {action: create|update|remove, type, actor, data, updatedFrom (previous values), webhookTimestamp}, HMAC-SHA256 signature header (timing-safe verify, ~60s window), 5s timeout, retries at 1min/1hr/6hr, auto-disable on persistent failure. Their docs steer everyone to webhooks over polling.

Build (scoped down): ONE user-configurable webhook URL (per user or per project) firing on task/flow/review events. Copy Linear's payload anatomy and HMAC discipline verbatim; skip their category breadth. This converts Tasker from pull-only into a system that can TRIGGER agent runs — "task entered review" kicks a CI job or a Claude Code hook; "flow step unblocked" wakes an executor. Strongest wedge extension found in the research: today agents come to Tasker; with this, Tasker state can start work.

Pairs with the magic-words task (that's inbound GitHub→Tasker; this is outbound Tasker→anywhere).

## Build spec — locked 2026-07-11 (my recommendation) — HIGHEST EFFORT of the spine; sequence AFTER 376
- `webhooks` table: (id, user_id, project_id nullable, url, secret, events text[], active bool, failure_count int, created_at).
- Payload (copy Linear verbatim — proven shape): {action: create|update|remove, type, actor, data, updatedFrom (previous values), webhookTimestamp}. HMAC-SHA256 signature header, timing-safe verify, ~60s window.
- Delivery: do NOT POST synchronously inside MCP write handlers (slows writes). RECOMMENDED: enqueue into a `webhook_deliveries` table on mutation; a scheduled/pg_cron drain function POSTs with the retry ladder (1 min / 1 hr / 6 hr), 5 s timeout, auto-disable on persistent failure.
- Settings UI: configure + test-fire the URL.
Strategic note: this is what turns Tasker from pull-only into a system that can TRIGGER agent runs ("task entered review" kicks CI / wakes an executor). The `actor` field in the payload depends on TDE-375.

## Path B (OUTBOUND) BUILT & DEPLOYED — 2026-07-13
Shipped and live (frontend on Netlify, mcp + new webhook-dispatch fn on Supabase, 2 migrations applied to prod):
- Tables: `webhooks` (url, per-endpoint secret, events[], active, failure_count) + `webhook_deliveries` (append-only queue w/ status/attempts/next_attempt_at/retry ladder). RLS: owner manages hooks + reads own deliveries; service role enqueues.
- Emitter: `emitWebhook()` in the MCP fn, fire-and-forget (never blocks/fails a write). Wired on update_task → `task.updated`, complete_task → `task.completed`, submit_task_review → `review.submitted`. Payload = Linear's shape {action,type,actor,data,updatedFrom,webhookTimestamp}; `actor` uses TDE-375 provenance.
- Delivery: `webhook-dispatch` edge fn does ALL signing/sending — HMAC-SHA256 over the body (`X-Tasker-Signature` + `X-Tasker-Timestamp` + `X-Tasker-Event`), 5s timeout, retry ladder 1min/1hr/6hr (4 attempts), auto-disable after 20 consecutive dead deliveries, resets failure_count on success. Driven by pg_cron every minute → net.http_post → the fn; cron→fn auth via a DB-generated Vault secret (never in the repo), read by cron in SQL and by the fn via a service-role-only RPC.
- Settings UI: Settings → Outbound Webhooks — add endpoint (URL + event checkboxes), one-time secret reveal, enable/disable, remove, "Send test", live delivery log with status chips.
