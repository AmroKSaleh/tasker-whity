Bringing the web app in line with the Flow redefinition (canonical definition on TDE-792; MCP directive already rewritten and deployed in TDE-808).

THE BUG THIS FOUND — an ungated flow was invisible on every surface. useFlows discovered flows purely as connected components of the I/O graph: detectFlows skipped any task with zero edges, and flow_id was consulted only afterwards to look up the flow name. Gates are now OPTIONAL, so a flow can legitimately have no contracts and therefore no edges — and name_flow will happily create one (its gate iterates declared edges only, so zero edges = zero violations). Such a flow did not appear on the Flows page at all, while its tasks were already hidden from the board by flow_id (TDE-320). The work vanished from everywhere at once.

This was unreachable under the old policy ("a flow with no contracts is just ordered tasks"), so it never bit. Retiring that policy made it live.

WHAT WAS CHANGED
- lib/flowGraph.js — detectFlows now builds adjacency from I/O edges AND shared flow_id, and admits a component whose tasks carry a flow_id even with no edges.
- lib/flowGraph.js — flowGateStatus returns edgeCount, so "no violations" and "nothing to violate" stop rendering identically.
- lib/flowGraph.js — flowSteps tie-breaks on flow_step before sort_order. With no edges every task sits at topo depth 0, and sort_order is board ordering that says nothing about sequence.
- hooks/useFlows.js — added flow_step to the select (it was not fetched).
- pages/FlowsPage.jsx — GateBadge gained a fourth state, "○ Ungated". Previously a flow with no declared handoffs rendered "✓ Contracts blessed", claiming a guarantee nothing was providing.
- Empty state, FlowStepList and FlowTaskPanel copy — "No output contract set." / "No acceptance rules set." read as deficiencies. They now say ungated is a legitimate state, and name the actual risk (a later step building on this without re-checking it).

STILL NOT DONE (deliberately, tracked elsewhere)
- The public docs page still teaches the retired definition — TDE-813.
- Progress display honesty when a flow gains steps mid-run — TDE-811.
- The handoff-vs-seam modelling gap: declaring an edge FORCES a blessed contract on both sides, so there is no way to record "step 2 uses step 1's output" without gating it. Agents will just stop declaring edges and the I/O graph loses information. That is a code change belonging to the rebuild decision on TDE-792 — see the finding recorded on TDE-808.

Correction to the "still not done" list above: the public-docs task is **TDE-812**, not TDE-813 (that is this task — a self-reference typo made at creation).

Also done in this pass, beyond what is listed: the FlowTaskPanel copy audit that TDE-812 had queued as a milestone. Its "No acceptance rules set." and "No output contract set." strings were changed here. ContractEditor.jsx was checked and needs nothing — it is a pure rule editor with no copy asserting that contracts are required.

## CLOSED 2026-07-29 — what was verified, and what was accepted rather than observed

Be precise about the evidence here, because the two halves differ.

**VERIFIED DETERMINISTICALLY (logic).** The real V2/app/src/lib/flowGraph.js — the module the Flows page uses — was exercised directly in node against an ungated flow (shared flow_id, zero I/O edges, no contracts, with sort_order deliberately REVERSED against flow_step to prove ordering does not come from board position). 10 checks, all passing:
- detectFlows finds the flow at all, with both tasks in the component. This is the original bug: before the fix, a component with no edges and no flow_id link was skipped entirely.
- flowGateStatus returns edgeCount=0 AND ok=true. Because GateBadge branches on edgeCount===0 BEFORE gate.ok, that combination renders "○ Ungated" and not the false "✓ Contracts blessed".
- flowSteps orders one-then-two off flow_step, ignoring the inverted sort_order, and numbers the steps 1,2.
- REGRESSION GUARD: a task with no edges AND no flow_id still yields zero flows — the flow_id change did not turn loose tasks into flows.
- CONTRAST: a gated, blessed two-step flow still reports edgeCount=1 and ok=true, so the ungated path did not swallow real gates.
Server-side truth confirmed too: get_flow_audit on the fixture reported "2 tasks | 0 edges validated | 0 AI-QA'd contracts", i.e. genuinely ungated rather than accidentally contracted.

**ACCEPTED, NOT OBSERVED (rendering).** No screenshot or human report of the Flows page is recorded. The user directed this task closed on 2026-07-29 after being shown the above. The rendered appearance of the "○ Ungated" badge is therefore inferred from the badge's branch condition plus verified input data — not witnessed. If the page ever looks wrong despite this, the fault is in GateBadge's markup or styling, not in the detection/ordering logic, which is now covered.
