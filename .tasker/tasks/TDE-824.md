WHY: You cannot currently ask Tasker "when was this task last edited?". The data has existed since 2026-07-14 — migration 20260714213000_tasks_updated_at.sql added tasks.updated_at with a touch trigger for Local Mode's LWW conflict resolution (TDE-410) — but all 42 references to it in V2/supabase/functions/mcp/index.ts are sync plumbing. No read tool has ever shown it.

THE BUG THAT MAKES THIS MORE THAN A DISPLAY TASK: get_task auto-flips a pending task to in_progress (index.ts ~4466). That is an UPDATE, so the touch trigger stamps updated_at = now(). A pure read therefore destroys the task's real last-edit time. Surfacing the field without fixing this would ship a column that mostly records when an agent last glanced at the task.

DECISIONS SETTLED (2026-07-30, with the user):
- Extend the EXISTING read tools rather than mint a new one. Reason: TDE-378 (MCP tool-surface diet) is open and high priority, and agents should see the timestamp inside the tools they already call. A dedicated get_task_timestamps tool was considered and rejected.
- Fix the pollution by PRESERVING updated_at across the autostart write, keeping autostart behavior itself intact. Flipping get_task's default to peek was considered and rejected — the whole directive playbook is built around autostart.
- The TDE-819 lifecycle event still records the autostart flip, so suppressing the touch loses nothing from the audit trail.

WATCH-OUT: the existing trigger cannot be fixed by simply passing the old value back. It reads `if new.updated_at is not distinct from old.updated_at then new.updated_at := now()` — passing the identical old value is "not distinct", so it still gets stamped. Suppression needs a transaction-local GUC (set_config('tasker.suppress_touch','on',true)) checked by the trigger, driven from an RPC, because the MCP writes through PostgREST with the service-role key.
