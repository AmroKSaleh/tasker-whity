From Linear: linear.new opens a new-issue composer prefilled from query params (title, description markdown, status, priority, assignee, labels, project, template); Cmd+K on any issue reverse-generates a "copy pre-filled create issue URL."

Build: a /new route on the web app — smarttasksxdd.netlify.app/new?title=...&detail=...&project=...&priority=... — opening the existing CreateTaskModal prefilled (auth-guarded; the pending-invite localStorage pattern from InvitePage already solved the login-redirect dance). Reverse affordance: "copy prefilled link" from a task.

Why it matters: gives every surface WITHOUT MCP (email, Slack, a chat UI, another AI product, a teammate) a zero-API way to hand work into durable state — the bridge for the non-MCP path. An agent that can only output text can still output a clickable URL that becomes a real task.

## SIZED 2026-07-31 — smaller than it looks, most of what it needs already exists

Checked the actual code before estimating rather than guessing. Verdict: SMALL, not a big build. No backend/MCP/schema changes needed at all — everything routes through client-side code against APIs that already do what's required.

**Three pieces already exist, reusable as-is:**
1. **Auth redirect-back is free.** `app/src/pages/LoginPage.jsx:14` already supports a generic `?next=<path>` param (`new URLSearchParams(location.search).get('next') || '/home'`) — works for ANY route, not just invites. An unauthenticated visitor hitting `/new?title=...` just gets sent to `/login?next=/new?title=...` and lands back exactly where they started, fully intact, after logging in. The task's own note assumed the InvitePage localStorage-token pattern would need copying — it doesn't; the generic `next` param is simpler and already there.
2. **Prefilling extra fields is free.** `app/src/hooks/useTasks.js:209` — `createTask(sectionId, text, groupId, extras = {})` already spreads `extras` directly into the insert (`...extras`). Passing `{ detail, priority }` today requires zero changes to task creation itself.
3. **Backlog-section fallback logic already exists** — `CreateTaskModal.jsx:18-20` resolves or creates a project's Backlog section on the fly when none is picked. Copy this pattern rather than reinvent it.

**What's actually new — one route + one small page:**
- A `/new` route in `App.jsx` (public — auth check happens inside the page, same as AuthGuard's pattern, not at the router level, since query params need to survive the login round-trip).
- `NewTaskPage.jsx` (new component, ~100-150 lines): parse query params (title, detail, project, priority) → resolve the named project by slug/prefix (same pattern as the MCP's `resolveProject`, just as a client-side Supabase query) → resolve/create its Backlog section (copy CreateTaskModal's fallback) → small form showing the prefilled fields, editable → Create button → call the existing `createTask` → success state (redirect to the project board, or a simple confirmation).
- The reverse affordance the original scope also asks for: a "copy prefilled link" button somewhere on an existing task's detail view — just string-building a `/new?...` URL from the task's current fields and copying it to the clipboard. Small, independent of the rest.

**Not needed:** any MCP tool changes, any database migration, any changes to `createTask` itself. This is a pure web-app addition.

Ready to execute in a fresh conversation — this note is written to be actionable without re-deriving any of the above.
