Filed 2026-08-06 from a real failure on the WQW (Waqtak Website) project. This is a design gap rather than a bug, and it caused a materially wrong deliverable that would have been sent to the user's manager.

**The shape of the problem**

get_project omits per-task Notes (the detail field) by default, "to keep the map small on large projects", and offers include_notes:true as the alternative. On WQW, with roughly 130 tasks and several task bodies running to multiple thousands of tokens, include_notes:true is not a usable option. So in practice the ONLY affordable overview returns task title, priority and status.

The trouble is that a title and a status are frequently the LEAST current fields on a task. Bodies get appended to as work progresses. Titles are written once, at creation, when the least is known.

**What actually happened**

An agent was asked to write a project update. It called get_project, read titles and statuses, and produced a status report stating that the site's security compromise entry vector "has not been closed" and that "every other workstream is being built on a host that may still be reachable."

That was false. Reading the task BODIES afterwards showed:

- WQW-160 (title: "Close the real entry vector", status: pending, priority: rush) had shipped its Step 1 mitigation on 2026-07-27, with regression verified. Step 3 was deliberately deferred by the owner for a documented reason. Step 2 belonged to a different team. The status "pending" was technically true and completely misleading.
- WQW-136 (title: "Repair Wordfence and run a full malware + database scan", status: pending) had already completed a production core hash against WordPress 7.0.2 with zero modified and zero missing files, plus full database, webroot, uploads, .htaccess, cron and user checks. Only the Wordfence repair itself remained.
- WQW-137 (title: "Get host access logs — find the entry vector and creation date") records that the logs are confirmed gone, the incident predates every surviving log file, and the task should be reshaped to closing candidate surfaces. Anyone acting on the title would go hunting for logs that do not exist.
- WQW-159's title read "zero submissions means delivery has never been proven" long after the body had recorded the forms as tested and working. The title was the sole carrier of a false premise, and it caused a second agent error later in the same session.

Every one of those errors came from the cheap call. The expensive call would have been correct. That is the wrong way round: the affordable path should not be the one that misleads.

**Why "just read the bodies" is not the answer**

Reading bodies costs roughly 4,600 tokens per task today (see the companion task on Instruction Set duplication; even fixed it would be ~1,600). Reading 130 of them to write one status update is absurd. The agent cannot know WHICH bodies contradict their titles without reading them, which is the circularity at the heart of this.

**Suggested options, cheapest first**

1. **Return the first N characters of detail** (say 200 to 300) alongside each title. Cheap, and would have exposed every one of the four cases above, because in each the body opens with a status or correction heading.
2. **Return a staleness signal**: detail_updated_at versus created_at, or a simple flag when the body has been substantially appended to since the title was last edited. Lets an agent know which tasks to open.
3. **Return the LAST heading or last paragraph of detail** rather than the first. Task bodies on this project accrete chronologically, so the most recent state is at the bottom. This may be the single highest-signal cheap field.
4. **A dedicated get_project_summary** that returns title, status, and a model-generated or last-written one-line current-state per task, maintained as a real field that update_task can set.

Option 3 combined with option 1 would likely have prevented the incident entirely, at a cost of maybe 40 tokens per task.

**Related, and worth solving together**

Task titles have no length limit and no staleness handling. WQW-134's "title" is a full multi-paragraph remediation document including a PHP code block, and it is returned in full by every get_project call, inflating the very response this task is about. Consider a title length cap or warning at create_task time, and a nudge to update the title when a task's body records a status change that contradicts it.

**Verification**
Take a project where at least one task's body contradicts its title. Call the overview. An agent reading only that output should be able to tell that the task needs opening.
