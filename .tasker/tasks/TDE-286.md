DISCUSSION TASK — captures the 2026-06-19 conversation re: 3rd-party integrations (branched off TDE-155). For later discussion, not ready to build.

## The use case (user's framing)
Single-player wedge into a team context: ONE user adopts Tasker; the team stays on Slack and does NOT use Tasker. Tasker bridges the individual across the two surfaces — they IMPORT tasks from the team's Slack, and REPORT progress back to Slack. Requires zero team buy-in → legitimate Phase 1 land-and-expand (NOT Phase 2, contrary to first assumption). ICP is broader than developers: "anyone with AI deeply in their workflow."

## Agreed direction
- This is the one case that justifies Tasker holding the integration itself (Model 1 = Tasker-as-hub, holds OAuth token, calls Slack API) rather than leaning on the agent's connector — because value is outbound to the team's shared Slack + inbound from team channels, which must be reliable and not depend on an AI session being open.
- Follow the EXISTING pattern: Slack would mirror the GitHub integration (github_connect + OAuth token table + edge-function callbacks). Not inventing the hub pattern — adding a 3rd provider. Lowers cost.

## The key differentiation (don't skip this)
The Slack pipe itself is COMMODITY — Todoist/Asana/ClickUp/Linear all do "import Slack msg → task" and "post status to Slack." Building that = a worse incumbent clone. Tasker's edge is what happens AFTER the task comes through the pipe:
- Import = agent reads the thread, understands context, creates a STRUCTURED task with a contract/flow (fuzzy "is this actually a task + what's the real deliverable" judgment = LLM strength).
- Report = VERIFIABLE progress (judge/contracts), not a checkbox echo.
→ Target architecture is HYBRID: Slack app = conduit (OAuth, "Send to Tasker" message shortcut, channel read, outbound webhook); agent = judgment (extraction, structuring, reporting). Productized AND AI-native = the part incumbents can't copy.

## Sequencing / scope
- Do REPORTING before IMPORT. Reporting is clean (structured data → message, reliable, demoable). Import is fuzzier (noisy threads, dedup, "is this a task?").
- Watch the google-calendar trap: Tasker already built its own Google Calendar integration while the agent ALSO has a GCal connector = duplicate. Settle the principle "when does Tasker build its own integration vs defer to the agent's?" — answer: build Model 1 only for agent-ABSENT, event-driven cases; defer to agent for agent-present convenience.

## Positioning fork to decide on purpose
Widening to "anyone in a Slack-driven org" grows TAM but pulls on the razor-sharp current wedge ("AI-native task manager, MCP is the interface, for devs building with AI"). Slack-for-non-devs = a 2nd interface + 2nd ICP. Clean story that holds both: "Tasker is your AI-native personal work layer — it plugs into wherever your work arrives (repo via MCP, team's Slack) and turns it into structured, verifiable work."
