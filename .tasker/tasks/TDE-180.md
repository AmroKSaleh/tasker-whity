FIXED & verified live (2026-06-09).

Root cause (confirmed by live repro): NOT a failed update. The mutation always worked — the bug was the reported COUNT. delete_group read `const { count } = await sb.from('tasks').update(...).select('*', { count: 'exact' })`; the `count` field on a chained update/delete+select is unreliable in this supabase-js version and returns 0/null even on success. Proof: ran delete_tasks:true on a 1-task group → reported "0 tasks deleted" but the task was actually gone. So the misreport was cosmetic; group_id WAS being cleared on the keep-tasks path.

Fix (V2/supabase/functions/mcp/index.ts, case 'delete_group'): count affected rows via the returned data.length instead of the count field, use resolved group.id (not raw args.group_id), and surface update/delete errors. Also hardened move_task_to_group: empty string / "null" now treated as ungroup instead of an invalid-uuid error.

Verified post-deploy: created group+task, delete_group delete_tasks:false → now reports "1 task moved to ungrouped" and the task survives, ungrouped.

Swept index.ts for other count:'exact' usages — only list_groups, which ignores the count field (computes counts separately). No other handler affected.

Note: the WCC stale-group_id orphans (TDE-166) predate this and likely came from an older code path; TDE-166's render fix is the durable safety net regardless of source. Left an empty test section "ztest-tde180" in BPW (no MCP delete_section tool) — delete via app.
