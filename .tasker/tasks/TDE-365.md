ORIGIN: strategic discussion prompted by research on AI adoption in corporations. The specific concern is code churn: roughly 80-90% of AI-generated code gets accepted on first pass, then only ~10-20% survives later review and the rest is reverted, inflating churn and rework. (Aligns with public findings like GitClear's reports on rising short-lived / reverted code as AI coding tools spread.)

THESIS RAISED: Instruction Sets (IS) are the solution to this.

CONCLUSION (after pushback): IS is necessary but NOT sufficient. It attacks generation quality (house rules, patterns, constraints, and definition-of-done fed in up front) but the churn metric is fundamentally an ACCEPTANCE-DISCIPLINE problem. The leverage point is the gate between "generated" and "accepted." The disease in that 80/20 stat is that 80-90% got accepted before anyone verified it. Perfect IS still produces churn if everything is accepted blindly and requirements keep shifting.

FOUR CAUSES OF CHURN, and what IS touches:
1. Missing standards/context — IS fixes this.
2. No verification gate before acceptance — IS does nothing.
3. Fuzzy requirements (code was going to be rewritten regardless) — IS does nothing.
4. Volume incentives / reviewer fatigue / rubber-stamping (the organizational failure the source video is really about) — IS does nothing.
3 of the 4 are not solved by better instructions.

NUANCE: not all churn is bad. Iteration and refactoring are healthy. The churn worth killing is rework: code reverted fast because it was wrong on arrival. Wrong-on-arrival code that still gets accepted is by definition a review failure, which loops back to the gate.

IMPLICATION FOR CORE APP / TASKER PRODUCT: Tasker already owns the gate machinery (flow contracts, validate_output, task review, check vs judgment rules). IS is the front-loaded-standards half; the enforced gate is the acceptance half. Using IS without the gate is running the half that does NOT move the 80/20 number. Ranked by impact on that metric, the gate beats IS. The product story and Core App UX should treat IS + an enforced verification gate as ONE churn-reduction system, and make the gate at least as prominent and low-friction to apply as IS is.

NEXT STEP: decide how Core App surfaces and encourages the gate alongside IS — specifically whether a lightweight verification gate (a minimal contract that must assert before AI-produced work counts as "done") should be the default or a one-click add for AI-executed tasks, not just something reserved for full flows. Then spec that.
