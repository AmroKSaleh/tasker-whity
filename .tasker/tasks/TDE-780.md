CONTEXT (from the owner, 2026-07-27): this is about **choosing a backend that covers the security holes that currently exist**. Priority moved rush → high the same day.

Scope is therefore a BACKEND EVALUATION driven by security, not a feature build. Anyone picking this up should first make the holes explicit — the decision is unarguable until the list exists — and should read the prior art before proposing a migration:

- KB "Security: flows + project_instructions had RLS disabled — fixed (2026-07-05)" — a real past hole, and it was a policy gap, not a platform failure.
- KB "Gotcha: INSERT…RETURNING fails when a SELECT RLS policy self-references the table via a STABLE fn" — evidence that RLS here is subtle and easy to get wrong.
- Memory `project_environments_org_rbac_build`: the org/RBAC DB security spine shipped, but **MCP enforcement is still PENDING**. This is the largest known structural hole: the MCP edge function runs as SERVICE ROLE and therefore bypasses RLS entirely, so every MCP-exposed operation is protected only by hand-written checks in index.ts (resolveProject ownership filters), not by the database. A missed `.eq('user_id', …)` in any one of ~150 tool handlers is a cross-tenant leak that RLS would otherwise have caught.
- Decision `decision_whity_backend_2026_06_19`: Whity Core was evaluated as a replacement backend and DECLINED (full migration + security + second-deployment cost). Reserved only as a possible Phase-2 self-hostable edition. Do not re-propose it without new information.

OPEN QUESTION the task must answer before any migration is considered: are the holes (a) policy bugs in the current stack — in which case fix them in place and a backend change is unjustified — or (b) structural, i.e. Supabase's RLS model is too easy to get wrong at this surface area? Only (b) argues for changing backend, and even then the service-role-bypass problem follows the code, not the database: it exists because the MCP is trusted, and it would exist on any backend unless MCP authorization is enforced per-request.

Recommended first step regardless of the answer: enumerate the holes as a concrete list, then close the MCP enforcement gap. That is the highest-value security work available and it does not depend on the backend decision.

## AUDITED 2026-07-31 — the open question is ANSWERED: policy bug, not structural. Do not migrate.

The audit this task asks for ("enumerate the holes as a concrete list") is done. All 139 handlers and 312 query sites in supabase/functions/mcp/index.ts were checked. Full write-up: KB "MCP handler audit (2026-07-31)". Report: https://claude.ai/code/artifact/93264556-fbf2-48e1-bd04-53c5d82e4853

THE HOLE LIST — it has exactly one entry:
- `pull_google_task` (index.ts:6001) takes section_id from args and queries `sections` by id with NO ownership check, then inserts a task into that section's project. Cross-tenant WRITE. Tracked as its own task ("SECURITY: pull_google_task trusts an args-supplied section_id").

Everything else audited clean. A crude detector flagged 176 "unscoped" sites across 85 handlers; reading them, all but the one above are legitimate: (1) fetch-then-mutate — ownership-checked select, then mutate by primary key; (2) transitive scoping via resolveProject/resolveTask/resolveGroup then `.eq('project_id', project.id)`. `sections`, `groups` and `phases` have NO user_id column at all, so transitive is the only possible model for them. `user_api_keys` / `oauth_tokens` are the auth lookup itself and cannot be user-scoped by definition.

THE ANSWER TO THIS TASK'S OWN OPEN QUESTION: option (a) — policy bugs, fix in place. One missing check in 139 handlers, in a file that ALREADY contains the correct helper (`resolveGroup`, index.ts:3182, does the proper transitive ownership join). That is an oversight, not evidence that Supabase's RLS model is too hard to use here.

=> A BACKEND MIGRATION IS UNJUSTIFIED. PocketBase/Whity would relocate the same 312 hand-checked query sites to a different database and change nothing — because the service-role bypass follows the CODE, not the database, exactly as this task's own notes already suspected. Do not reopen the migration question without new evidence.

THE REAL RESIDUAL RISK (and the work actually worth doing): correctness rests on convention across 312 sites with zero database backstop, and that count grows with every tool added. The durable fix is a backstop, not a platform: either have the MCP act as the calling user so RLS applies, or force every handler through one choke-point helper that cannot be forgotten. Both are code changes.

RECOMMEND: rename this task from "Backend Services" to MCP authorization hardening, and drop the PocketBase framing — it points at work the evidence says not to do.
