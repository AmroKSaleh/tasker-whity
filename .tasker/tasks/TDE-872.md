Found 2026-08-04 while reading resolveProject for TDE-822. The original observation was a single leak on the project-prefix lookup; grepping the file showed it is a systemic pattern across TEN call sites in supabase/functions/mcp/index.ts, and one group of them behaves WORSE than the prefix case.

## THE BUG

Every one of these passes raw user input into a Postgres `ilike` pattern without escaping the LIKE metacharacters `%`, `_` and `\`. In a LIKE pattern those are wildcards, so user input silently becomes a query language:
- `_` matches any single character — `project_id: "T_E"` resolves to `TDE`.
- `%` matches any sequence — `project_id: "%"` matches every project the user owns.

## THE THREE SEVERITY CLASSES — do not treat them the same

**CLASS 1 — SILENT MIS-RESOLUTION. This is the real bug and the reason to file it.**
index.ts:3577, 6915, 7742 (and check 3366, 7481, 8402, which are the paginated/queried variants of the same flow lookup). Shape:
`ilike('name', \`%${args.flow_id}%\`).order('created_at', { ascending: false }).limit(1).maybeSingle()`
Because these ORDER BY created_at DESC and LIMIT 1, a wildcard input does NOT fail — it quietly returns the user's MOST RECENTLY CREATED flow. An agent passing a flow_id containing `%` or `_` operates on the wrong flow and gets no error at all. Every other class here fails closed; this one hands back a plausible wrong answer, which is the worst failure mode in the file.

**CLASS 2 — FAILS CLOSED, confusing error only.**
index.ts:306 `ilike('prefix', projectId)` and 406 `ilike('name', ref)` — both intend EXACT case-insensitive match, both end in `.maybeSingle()` with no ORDER BY. A multi-row match makes maybeSingle return null, so resolution reports "not found" rather than picking wrongly. 306 also logs to `mcp_error_logs`, so these are diagnosable after the fact. Same for 9357 (`flow_templates` name lookup).

**CLASS 3 — INTENTIONAL substring search, still wrong but low stakes.**
index.ts:5257 `ilike('title', \`%${t}%\`)` — a task-title contains-search. The fuzziness is the feature; unescaped input just makes the fuzziness slightly unpredictable. Fix for consistency, not urgency.

## SCOPE NOTE — this is NOT a security issue

Every query above is scoped by `.eq('user_id', userId)`, so nothing crosses a tenant boundary. A user can only wildcard-match their own rows. This is a correctness and predictability bug, not an access-control one. Do not escalate it as an injection vulnerability — LIKE metacharacter leakage is not SQL injection, the parameterization is intact.

## THE FIX

For CLASS 1 and CLASS 3 (genuine substring searches), escape the metacharacters before interpolating:
`const esc = (s) => s.replace(/[\\%_]/g, '\\$&')` then `` ilike('name', `%${esc(args.flow_id)}%`) ``. Postgres LIKE honours backslash as the default escape character, so no ESCAPE clause is needed.

For CLASS 2 (exact-match intent) escaping also works and is the smallest change. The cleaner expression of the intent is a case-insensitive equality rather than a pattern match at all — but note that switching line 306 to `lower(prefix) = lower(input)` requires either a functional index, an RPC, or normalized-on-write storage, and the uppercase-normalization decision is an open milestone on TDE-822. So: escape now (self-contained, no schema dependency); revisit 306 as equality only if TDE-822 decides to normalize prefixes on write. Do NOT block this bug on that decision.

Independently of the escaping, CLASS 1 deserves a second look at `.limit(1)` + ORDER BY as a resolution strategy: silently picking the newest match when a name lookup is ambiguous is a bad default even with escaped input. Ambiguity should probably return the candidates rather than guess.

## RELATIONSHIP TO TDE-822

TDE-822 (prefix length + uniqueness constraints) carries a milestone for the line-306 fix, written before the other nine sites were found. That milestone should defer to THIS task — the fix belongs here as one consistent pass, not split across two tasks with two different approaches. TDE-822 keeps the schema/constraint work.
