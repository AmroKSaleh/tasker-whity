The user requested to remove the 3-letter limit constraint when setting a project prefix.

## SCOPED 2026-08-04 — read this before starting. The length limit is the smaller half of this task.

Read the code first rather than trusting the one-line premise. The prefix system has no integrity constraints at all, and raising the length cap without fixing that makes collisions more likely, not less. Both belong in one visit.

### VERIFIED STATE (read from code 2026-08-04, not assumed)

- `projects.prefix` is declared `text DEFAULT ''` in supabase/migrations/add_short_ids.sql:2. **No NOT NULL. No UNIQUE constraint anywhere in the migrations.**
- The same migration has a ONE-TIME backfill (lines 38–49) deriving a prefix from the project name `WHERE prefix = '' OR prefix IS NULL`. It ran once. It does not protect rows created afterwards.
- Prefix-less projects are an EXPLICITLY SUPPORTED state, not an oversight — supabase/migrations/20260611100000_add_flow_short_id.sql:1 accounts for flow short IDs on "prefix-less projects."
- `resolveProject` (supabase/functions/mcp/index.ts:303–316) tries three lookups in order: exact `slug`, exact `id`, then `ilike('prefix', input)` — each one `.eq('user_id', userId)`, then `.maybeSingle()`.

So today's prefix uniqueness is not enforced by anything. It is the one-time backfill plus luck.

### THE LIVE DEFECT THIS EXPOSES

The **Abaq Website** project (id `7554862a-d5e1-43b8-aa23-fa74a6d388ca`, in the "New environment" environment) has an EMPTY prefix despite its name reading "Abaq Website - ABQ". Its 22 tasks cannot be addressed as `ABQ-n` — only by slug or UUID, since prefix is the last fallback. It was created after the backfill, which means at least one creation path does not set a prefix. Fixing the row is not enough; the path needs the constraint.

### HOW COLLISION FAILS TODAY — it fails CLOSED, which lowers the urgency

A duplicate prefix makes `ilike` match two rows, `maybeSingle()` then returns null, and resolution reports "not found" while logging to `mcp_error_logs`. That is a confusing error, NOT a silent mis-resolution to the wrong project. Treat this as a correctness/UX fix, not a data-integrity emergency — it matters, it is not on fire.

### SEPARATE BUG FOUND IN THE SAME READ — ilike wildcard leak

The user-supplied `project_id` is used as the `ilike` PATTERN, so `_` and `%` in it act as SQL wildcards. `T_E` resolves to `TDE`; `%` matches every project and then fails via `maybeSingle()`. Low stakes (own-data only, fails closed) but it is wrong. When touching this, either escape the input or switch to `lower(prefix) = lower(input)`, which is what the code actually means and is index-friendly.

### DECISION RECORDED — owner, 2026-08-04: NO addressing protocol

The owner asked whether to design "a structure for communicating with Tasker" for project addressing, given that current prefix uniqueness is accidental. DECIDED AGAINST, deliberately. Reasoning to preserve: a convention a human must remember is strictly weaker than a constraint the database enforces — it drifts the first time a project is created late at night through a different path, and the drift is invisible until a lookup fails. The owner addresses projects ONLY by prefix, so a broader addressing scheme has near-zero marginal value today. The constraint captures the value; the protocol does not earn its cost. Do not revive the protocol idea inside this task.

### DEFERRED TO PHASE 2 ON PURPOSE — the case that DOES need real addressing design

Prefix addressing breaks unfixably once projects are multi-user: two members of an org could each own a project prefixed `WEB`, and `resolveProject` scopes on `user_id` alone, so it cannot disambiguate them even in principle. That is the point at which addressing needs genuine design. It is not reachable yet — the entire MCP edge function contains exactly ONE occurrence of the string "org" and exposes no org tool, so org-owned projects are currently unreachable from MCP rather than merely unenforced. Phase 2, per the canonical phase model. Do not pre-solve it here.

### THE OPEN DECISION FOR WHOEVER PICKS THIS UP

What should the new maximum actually be? Removing the cap entirely is probably wrong: arbitrarily long prefixes stop short IDs being short, and start colliding with slugs in the human's head (slug is checked BEFORE prefix in the resolver, so a prefix that looks like a slug is genuinely ambiguous to a reader even though the code has a deterministic order). A bounded raise — 3 to 6, or 3 to 8 — likely satisfies the original complaint at none of the cost. Also decide whether to normalize prefixes to uppercase on write, since resolution is already case-insensitive and mixed-case storage buys nothing.

### SIBLING DATA CLEANUP — found in the same pass, NOT part of this task

Two duplicate project pairs exist with SPLIT task histories: Knowledge Extraction as `KE` (0/0 tasks) and `KEX` (0/3), and Waqtak Website as `WQW` (43/130) and `WW` (23/98). Their prefixes are distinct so resolution works fine — but a human saying "the Waqtak website project" is genuinely ambiguous, and neither board shows a true denominator. Both `KEX` and `WW` are also sitting in NO environment. This is a merge decision for the owner, not a prefix fix; filed here only so the finding is not lost.
