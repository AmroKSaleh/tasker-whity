Carried forward from TDE-865, which fixed only the HONESTY half by explicit scope decision (TDE-790, 2026-08-04). This is the other half, recorded so it is not lost inside a completed task.

WHAT IS NOW TRUE (after TDE-865): the connector tells the truth. A 401 on the account probe flips the status to invalid, Settings renders an amber reconnect prompt naming the reason, and the dead token is memoised in localStorage so the board stops firing a doomed /user request on every page load. The memo clears on saveGitHubToken / removeGitHubToken, which covers the OAuth re-login path.

WHAT IS STILL MISSING: nothing refreshes or proactively invalidates the credential. Recovery is entirely manual — the user must notice the amber state and reconnect. Two paths produce these tokens and neither handles expiry: TDE-91 auto-attaches a PAT captured at GitHub login (AuthGuard's captureGitHubToken), and TDE-75 uses the OAuth provider_token. A GitHub OAuth provider_token in particular is short-lived, which is the likely explanation for how this credential died in the first place.

THE DECISION TO MAKE FIRST — and it is the reason this is not simply "add a refresh call": can these credentials be refreshed at all? A classic PAT cannot; it can only be replaced by the user. An OAuth token may be refreshable if a refresh token was stored, and Supabase's provider_refresh_token is only present under specific settings. So the honest answer may be "always needs re-auth", in which case the work is not a refresh mechanism but a good re-auth prompt at the moment of failure rather than only in Settings.

NOT URGENT. The dangerous failure mode — a status indicator that lies — is already closed. What remains is a convenience gap: the user finds out when they look, rather than when it happens.
