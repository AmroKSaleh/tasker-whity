DELIVERABLE: a written design doc (not a build). Once signed off, a build flow follows. Reframed from the original rush "just add local functionality" after a long design discussion — see below.

## What the user wants (the real need)
Opt-in-per-project LOCAL-FIRST projects. When enabled at project creation, the project's tasks (and attached files) are mirrored to a GitHub-backed repo checked out on the user's device(s). The AI agent works the LOCAL files DIRECTLY (no MCP round-trip) — that's "stage 1", fast/local. Changes sync CONTINUOUSLY to the online Tasker app — "stage 2". The user wants a CONSISTENT mirror across MULTIPLE devices they use Tasker on. Default Tasker stays fully-online; local is OPT-IN per project.

## Direction AGREED in discussion (this is "Interpretation C", NOT the projection model)
- Local files are AUTHORITATIVE while working locally (agent edits them directly). This is what makes it worth having — pure one-way projection was rejected because it removes the local-authoring benefit.
- Online DB is the SYNC HUB all devices sync THROUGH (not peer-to-peer) — this is how N devices stay consistent without N-way merge.
- CONTINUOUS sync shrinks the divergence window to ~seconds, so conflicts are RARE; last-write-wins by modification time is an acceptable resolution rule (user's call). This is the engineering answer to conflict resolution — avoid divergence rather than solve merge.

## Why this is NOT the TDE-404 zombie (important context)
TDE-404 (closed: "don't build local-first") had INFREQUENT sync (daemon fires "when statuses change") → big divergence windows → real conflict hell. That's why it was killed. TDE-406-C is materially different: CONTINUOUS sync + (possibly) local contracts shrink both the conflict problem and the validation-lag problem to "rare + tolerable". The risk profile changed enough that the earlier rejection does NOT carry over. (TDE-404 itself shipped a SEPARATE thing — an MCP instruction rewrite so agents route durable work to Tasker by default — unrelated to this.)

## Open questions the DESIGN DOC MUST ANSWER
1. On-disk FORMAT: shape of .tasker/ (the V2/examples/blog-post-workflow/.tasker/ folder is a starting reference — project.json + tasks/*.md). What's the task file schema, how are attachments handled, how are I/O edges / flows / milestones represented.
2. SYNC PROTOCOL: what's the sync unit, change-detection mechanism (git commits? file mtime? a local change journal?), and the exact last-write-wins rule (field-level vs row-level; clock source given multi-device).
3. CONFLICT RULE: precise behavior when online and local (or device A and device B) edited the same task within the window. LWW-by-mtime is the default the user favors — spec the edge cases.
4. CONTRACTS location — the design must WEIGH local-vs-online contracts and RECOMMEND the v1 cut with rationale. Local contracts close the validation-lag gap (task validated at the moment it's marked done locally) but require porting contract_gate.ts into the local runtime and keeping TWO copies in sync (KB f2a336ba flags this gate logic is already mirrored in two places and painful to align). Online-at-sync-time is lighter for v1. DECISION DEFERRED TO THE SPEC.
5. LOCAL RUNTIME (the biggest fork, deferred out of this decision): where does continuous sync + on-write contract execution actually run? Options surfaced: (a) a local CLI/companion daemon the user installs (most robust, new distributable); (b) agent-driven, no daemon (lighter, but "continuous" degrades to "checkpoint" sync → wider windows → back toward TDE-404 risk). The spec should recommend one. Note the possible tie-in to the future CC plugin (could bundle the runtime).
6. GITHUB plumbing: token storage/scope per user, the webhook or mechanism that tells online-Tasker the repo changed, and the loop-breaker that stops online→repo and repo→online syncs from ping-ponging. Existing MCP tools github_connect / github_push_project / github_sync_issues are a partial starting point.
7. v1 vs v2 CUT: what ships first vs. deferred (contracts is one axis of this; multi-device may be another).

## Pros/cons already established (for the doc's context section)
Pros (most available even in lighter cuts): cheap zero-latency local reads; free git version history/diffs of task changes; tasks live where the code lives; diff-based human review of agent task changes; offline authoring (user says offline is NOT a real need — low weight).
Cons (mostly B/C-only, mitigated by continuous sync + local contracts): conflict resolution across online-hub↔devices; validation-lag rollback (closed IF local contracts); stateless hosted MCP can't run the sync loop itself (→ the runtime fork, Q5); GitHub token/security surface; source-of-truth cognitive cost.
