Found 2026-08-07 while restructuring TDE's sections.

SYMPTOM: list_sections reports task counts that no listing path can reproduce, and delete_section's non-empty guard trusts those counts — so a section that is empty by every readable measure cannot be deleted.

CONCRETE CASES (both live in TDE right now):
- Security (id 0e3544f5-be5e-458d-90a8-886fe626ec34): list_sections says 1 open / 1 total. delete_section refuses with "still has 1 task". list_tasks with section_id + status:"all" + include_flow_steps:true returns "No tasks found". list_groups returns none.
- Backlog (id f9edec45-7e58-4b74-8d2f-30f45906a98c): list_sections says 9 open / 12 total. Only 3 tasks (TDE-849/850/851, all done) are reachable via any listing.

EVIDENCE THAT RULES OUT THE OBVIOUS CAUSES:
- Not flow steps. Both TDE flows (TDE-F1, TDE-F2) are 6/6 done, and their 12 steps all report sections other than Backlog/Security.
- Not pagination. Both pages of a project-wide list_tasks (status:"all", include_flow_steps:true, 340 rows total, cursor exhausted) contain ZERO rows reporting "· Backlog" apart from the 3 dummies, and ZERO reporting "· Security".
- Not a rendering gap — the same listing correctly prints "· no section" for TDE-67, so section labels are reliable.

SECONDARY FINDING: include_flow_steps:true appears to be ignored when section_id is also passed. Worth checking as a separate defect in the same query layer.

WHY IT MATTERS: the counts on list_sections are what the board and any status report read. If they can drift from the actual task rows, every section-level number in the product is suspect, not just these two. The deletion block is the visible symptom; the wrong count is the actual bug.

DELIBERATELY NOT DONE: delete_section with delete_tasks:true would have cleared both sections, but destroying rows nobody can read is not an acceptable way to fix a count. Diagnose from the DB first.

NEXT STEP: query the tasks table directly for section_id in those two UUIDs and compare against what list_tasks' filters exclude — the difference is the bug. Likely candidates: a status value outside the pending/in_progress/done enum, a NULL status, or a soft-delete/archive flag that the count query ignores but the list query filters on.
