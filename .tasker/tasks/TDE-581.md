GAP found while doing a groups reorg on TDE entirely in Local Mode (2026-07-17).

THE GAP: the .tasker/ file format + flush_local_project can represent task field edits (status, priority, section, order) and deletes, and after a pull a task file DOES carry a `group:` field (read works). But there is no file/flush path to:
  1. CREATE a group (groups live in project.json, which flush treats as a regenerated snapshot and does NOT apply)
  2. MOVE a task into/out of a group (no writable group edge via flush)
  3. reliably MOVE a task across sections as part of a structural reorg batch
So any reorg that involves grouping falls back to MCP (create_group + move_task_to_group), which defeats the "work offline through files, one flush" model for exactly the organize-the-board use case. Confirmed empirically: flush only applies tasks/*.md; project.json edits are ignored.

WHY IT MATTERS: "audit & organize the board locally" is a prime Local Mode use case (cheap bulk reads), but the WRITE half of organizing (grouping, section restructure) is currently MCP-only. Closing this makes Local Mode a complete reorg surface.

SCOPE TO DECIDE (open questions):
  - Should flush accept group create/rename/delete (e.g. via an applied project.json diff, or a dedicated groups manifest file) rather than treating project.json as read-only?
  - Make `group:` in task frontmatter a WRITABLE field that flush honors (create-by-reference: unknown group slug in a task → create it), or require explicit group declarations first?
  - Same question for section create/move via files.
  - Conflict/LWW semantics for structural ops (two devices adding groups) — needs a rule like the task LWW.

POINTERS: sync engine = TDE-410 (pull/flush LWW+leases); format loader/serializer = TDE-408; related umbrella = TDE-534 "Increase the functionality of local projects" (Flows-in-local is the sibling gap). Local Mode design doc: V2/docs/local-first-design.md. See KB entries "Local Mode v1 SHIPPED" (TDE-F2) and "Local Mode design AGREED" (TDE-406).

NEXT STEP: decide the file-format representation for groups (writable frontmatter vs. manifest) before any build.
