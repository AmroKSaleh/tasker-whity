Fell out of Q6 of the Flows redefinition (TDE-798, 2026-07-28) and confirmed by the user as worth doing.

THE PROBLEM: a flow does not necessarily know its full step list when it starts. Some operations discover their next step as they go — research and investigation are inherently like this. Q6 deliberately REFUSED to make that a flow "type" (there are no flow types; see TDE-798), which means the system cannot solve it by branching on a flag. It has to be handled by the progress readout itself always telling the truth.

The failure mode: a readout that says "3 of 7" when the 7 is not knowable. It looks precise, it is wrong, and it silently under-reports remaining work — the same class of bug as TDE-806 (two denominators disagreeing) and the reason the phases aggregate bar carries an explicit unphased segment rather than a silent residual. A progress indicator that lies is worse than one that admits it does not know.

WHY IT MATTERS BEYOND TIDINESS: the whole point of a flow is legibility across a long operation ("hold it together" — one of the two motives in the canonical definition, TDE-802). A progress readout that misstates the total attacks the exact property the feature exists to provide.

Related: TDE-798 (Q6 — no flow types), TDE-802 (Q10 — the two motives), TDE-806 (the flow-steps-in-card-counts bug and its two-denominators lesson), and the phases PhaseBar precedent of never rendering a silent residual.

Note the Flows section is otherwise parked pending the rebuild decision — this is a small honesty fix, not a Flows build.

## SHIPPED + DEPLOYED 2026-07-29 — branch tde-811-honest-flow-progress

### MILESTONE 3'S PREMISE WAS FALSE — there was no frozen denominator
Milestone 3 said "make the denominator track steps added after instantiation instead of the count frozen at start." **Nothing was frozen.** Verified: the `flows` table has never had a step-count column (20260605140000_add_flows_table.sql: id, user_id, project_id, name, context, created_at, updated_at); the web app computes `stepCount: steps.length` live in useFlows.js; every MCP readout counts the current task list (`sorted.length`, `guideSorted.length`, `total`). The fraction already tracked additions correctly, and a mid-run add was proven live to move 1/1 → 1/2 with no code change needed. That milestone required no work.

### THE ACTUAL BUG — a false TERMINAL VERDICT, not an imprecise fraction
`run_flow` computed `allDone = completedCount === sorted.length`, printed **"Status: COMPLETE — all steps done."** and **returned early**. `advance_guide` did the same via `remaining.length === 0` → "Flow complete — all steps done."

For an operation that discovers its next step as it goes, that condition is true at EVERY pause. Finish step 1 of an eventual 5 and the flow declares itself complete, then silently reverts to in-progress when step 2 appears. This is worse than a wrong number because it changes behaviour: run_flow's early return means an agent reading COMPLETE **stops working**.

### THE FIX — one mutable fact, not a flow type
New column `flows.step_list_open boolean not null default false` (migration 20260729120000). Deliberately NOT a flow "type" — Q6/TDE-798 refused those and was right: nothing branches on a *category* of flow. This is a statement about what is currently KNOWN, it flips either way mid-run, and it changes nothing about execution except whether the system is entitled to call the flow finished. Default false because most flows are authored whole by build_new_flow; defaulting open would tax every readout to serve the uncommon case.

Wired into:
- **run_flow** — when open and all known steps are done: reports "ALL KNOWN STEPS DONE — but this flow's step list is still open, so it is NOT finished", lists the steps so far, and tells the caller to create the next step or close the list. Critically it still returns, but without the COMPLETE verdict, so nothing reads as terminal. When closed: "COMPLETE — all N steps done."
- **guide_flow** — progress line appends "— step list OPEN, more steps expected".
- **advance_guide** — replaces "Flow complete" with the all-known-steps-done wording when open.
- **list_flows** — an open flow does NOT roll up to `done` even at 2/2; renders "2 known so far · 2/2 done · in_progress · step list OPEN (more steps expected)".
- **update_flow_context(step_list_open)** — the setter, both directions.
- **name_flow(step_list_open)** — declarable at creation. Guarded: the field is written ONLY when the caller passes it, so re-calling name_flow to add a step does not silently slam an open list shut.
- **New global directive** ("STEP LIST OPEN") telling agents to set it at authoring time if the steps aren't listable to the end, to open it the moment they realise remaining work isn't knowable rather than waiting until the readout is already lying, and to CLOSE it once the extent is known — since an open list permanently withholds the flow's ability to report itself finished.

### VERIFIED LIVE (milestone 4), on a throwaway flow since deleted
1. Flow named with step_list_open:true, its single known step completed → run_flow reported "Progress: 1/1 steps done — step list still OPEN" and "ALL KNOWN STEPS DONE … it is NOT finished". Under the old code this printed "COMPLETE — all steps done."
2. A step added mid-run via name_flow WITHOUT passing step_list_open → denominator moved to 1/2 and the flag SURVIVED (the guard works).
3. list_flows while open at 2/2 → status `in_progress`, not `done`, with the OPEN annotation.
4. update_flow_context(step_list_open:false) → run_flow then correctly printed "COMPLETE — all 2 steps done."
Type errors unchanged at the pre-existing baseline of 32, none referencing the new code.

The web app's own `useFlows` status derivation (`doneCount === steps.length ?
