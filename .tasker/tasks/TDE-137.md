⚑ REFRAMED 2026-06-04 (see KB "Flow's Messaging Angle" for the full reasoning). 137 is NOT a "workflow engine / flow runner." It is the CONTRACT LAYER. The agent (Claude Code) is the engine — it already orchestrates, self-iterates, and persists tasks natively, so building a runner would be redundant with the platform. 137's job is the part agents DON'T give themselves.

## Goal
Let the HUMAN author an explicit quality contract on each handoff, persist it, check it at each step, and route structured feedback back — so the agent can't quietly declare premature ("hallucinated") completion. Differentiation = external human-authored contracts + durable/visual/reusable artifact (Blueprint, templates), NOT orchestration.

## Decided design
- AGENT-EXECUTED VIA MCP: Tasker holds the steps/order/contracts/state + does cheap deterministic checks; Claude Code does the work AND the semantic validation (its own Claude judges "does this meet the bar?"). Tasker makes NO paid AI calls.
- DEV/MCP-EXCLUSIVE: this is why validation is free and sidesteps the in-app-AI cost question (TDE-169). Non-dev web-app users don't get Flows.
- SUPERVISED AUTOPILOT, not fire-and-forget: pauses at human-only steps, outward/risky actions (manual-push rule), and unresolved validation failures.

## Scope of 137 (the foundation — shippable alone)
- Upgrade input/output from a thin "type" into a real human-authored CONTRACT (what this task must produce + what the next expects + rules to check against).
- validate_output: deterministic checks in-MCP; semantic judgment DELEGATED to the agent (return the contract + a clear instruction for the agent's Claude to judge — mirror the "presentation/directives" pattern). No server-side LLM.
- Store structured feedback on the task (feedback ledger) and REOPEN the failed task on a failed handoff (single handoff).
- A clear flow protocol the MCP returns so the agent knows: get next → read contract → do work → record output → validate → pass(advance)/fail(reopen).

## Boundary with TDE-156
137 = author contracts + validate one handoff + store feedback + reopen the failed task. 156 = the multi-step revision LOOP (retry cap 3, reopen ≤2 upstream then ask human). Keep 137 small; 156 layers the cascade on top.

## Already built
set_task_input / set_task_output / validate_output / get_validation_feedback + input/output data model (migration 20260529120000_add_task_io.sql). 137 = upgrade these to the contract framing + agent-delegated validation, not build from scratch.

## ORIGINAL SPEC — HISTORICAL (superseded by the reframe above; kept verbatim for full cross-device context)
═══════════════════════════════════════════════════════════

Build the core workflow engine: tasks can declare what input they need and what output they produce, with validation and feedback communication.

### Data Model
Add to tasks table:
input: {
  source_task_id: string (UUID or short ID),
  expected_type: "string" | "document" | "code" | "decision" | "other",
  validation_rules: "user-defined rules or AI-powered"
}
output: {
  target_task_id: string (UUID or short ID),
  validation_status: "pending" | "valid" | "invalid",
  feedback: string (what's wrong, what to fix)
}

### Validation Logic
Context-aware validation: parse the output from source task, validate against target task's expectations.
Validation approaches:
- Simple: type checking ("is this a document?")
- Context-based: check against user-defined rules ("must contain sections X, Y, Z")
- AI-powered: use Claude to validate ("does this implementation match the design?")
When validation fails: set output.validation_status = "invalid"; set output.feedback with specific error/guidance; notify source task ("your output didn't pass validation, feedback: ..."); source task can see feedback and iterate.

### MCP Tools (the original 4)
1. set_task_input — Set what a task expects (task_id, source_task_id, expected_type, validation_rules) → confirmation
2. set_task_output — Set where output goes (task_id, target_task_id) → confirmation
3. validate_output — Check if task's output is valid for target task (task_id) → {status, feedback}
4. get_validation_feedback — See what feedback target task sent (task_id) → feedback string or "no feedback yet"

### Workflow Example (original framing)
1. Task A (implement feature) → output goes to Task B
2. Task B expects: "code that passes linter and tests"
3. Person completes Task A, marks it done
4. System validates output (does code pass linter? do tests pass?)
5. If invalid: Task A gets feedback "tests failing: X, Y, Z"
6. Person sees feedback, iterates on Task A
7. Once valid, Task B can proceed

### Implementation Steps (original)
1. Add input/output fields to tasks table (Supabase migration)
2. Add MCP tools (set_task_input, set_task_output, validate_output, get_validation_feedback)
3. Implement validation logic (context-aware, parsing-based)
4. Test with MCP (Claude Code users can set up workflows)
5. No visualization yet — system works entirely via MCP and task data

### Why This Matters (original)
Moves Tasker from "task organizer" to "workflow engine." Solo devs can chain tasks (output→input), get feedback when work doesn't meet expectations, see validation errors and iterate, build complex projects with clear dependencies. Phase 2 visualization shows this as a graph (like Unreal blueprints), making it the USP.

### Testing (original)
Create test tasks with input/output relationships; use MCP tools to validate + see feedback; verify validation catches mismatches; verify feedback flows correctly.
