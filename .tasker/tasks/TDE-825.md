Found during the MCP handler audit (TDE-817), 2026-07-31. This is the ONE confirmed authorization hole out of 139 handlers — everything else audited clean.

THE BUG: supabase/functions/mcp/index.ts, the `pull_google_task` handler, line 6001:

    const { data: section } = await sb.from('sections').select('project_id').eq('id', section_id).maybeSingle()
    if (!section) return 'Section not found.'

`section_id` comes straight from the caller's args. There is NO ownership check — not on the section, not on its parent project. The handler then inserts a task using that section's project_id.

WHY IT IS EXPLOITABLE: the MCP edge function runs as SERVICE ROLE (index.ts line 11), so RLS is bypassed on every query. Ownership is enforced only by hand-written filters, and this handler has none. A caller who knows or guesses another user's section UUID can insert a task into that user's project and section. The inserted row carries the ATTACKER's user_id but the VICTIM's project_id/section_id — so it lands on the victim's board with attacker-controlled title and body (pulled from the attacker's Google Tasks account).

Impact: cross-tenant WRITE / content injection into another tenant's workspace. Not a read leak. Harmless today (single real user) and it becomes live the moment there is a second account — i.e. exactly at launch.

THE FIX: `sections` has no user_id column — section ownership is transitive (section → project → user). The codebase ALREADY has the correct pattern; copy `resolveGroup` (index.ts line 3182), which does the transitive join and compares user_id:

    const { data: group } = await sb.from('groups')
      .select('*, sections(id, project_id, projects(id, user_id))')
      .eq('id', groupId).single()
    if (!group || group.sections?.projects?.user_id !== userId) return null

So: add a `resolveSection(sb, userId, sectionId)` helper on the same shape and use it here. Worth grepping for other args-supplied section_id uses at the same time, though the audit found the rest are all scoped via `.eq('project_id', project.id)` where project came from resolveProject.

VERIFY AFTER FIXING: call pull_google_task with a section_id belonging to a different account and confirm it returns "Section not found." rather than inserting.

WHY THIS MATTERS BEYOND THE ONE BUG: it is the evidence for TDE-780's open question. The hole is a POLICY BUG (one missing check where the right helper already existed), not a structural failure of Supabase's model — which means a backend migration is unjustified. See the audit KB entry for the full reasoning.

## FIXED + DEPLOYED + VERIFIED 2026-07-31

Branch `tde-825-resolve-section-ownership`, commit 1e0ad71, pushed. NOT merged — awaiting explicit go-ahead.

WHAT CHANGED (supabase/functions/mcp/index.ts):
- Added `resolveSection(sb, userId, sectionId)` next to resolveGroup — does the transitive `sections → projects → user_id` join and returns null on mismatch. Carries a comment explaining WHY a bare .eq('id', …) is unsafe here (service role, no RLS backstop), so the next person doesn't reintroduce it.
- `pull_google_task` now routes through it and uses the resolved `section.id` / `section.project_id` rather than the raw arg.

VERIFICATION (both observed against the same deployed build, not asserted):
- Owned section_id (f9edec45… Backlog) → `Pulled "Test for the app" → task 826`. Throwaway task deleted after.
- Non-owned section_id (3f8e21ac-77b1-4d0e-9c22-6a5f0b9e4d13) → `Section not found.`
- `deno check`: 32 errors before and after, identical set — all pre-existing implicit-any noise, none introduced.

MILESTONE 3 RESULT — pull_google_task was the ONLY one. Re-checked every args-supplied section_id/group_id/phase_id reaching a query. The rest are all guarded: `list_tasks` (base query is .eq('user_id', userId), so a foreign section_id just matches nothing), `list_groups` / `create_group` / `analyze_section` / `section_insights` (all scoped by .eq('project_id', project.id) from resolveProject), `rename_group` / `delete_group` (resolveGroup first).

## ⚠ SECOND BUG FOUND WHILE VERIFYING — pull_google_task had NEVER worked

The positive test surfaced an unrelated, pre-existing defect: the handler read and wrote **`sorting_order`**, but the column is **`sort_order`**. The insert therefore failed unconditionally with "Could not find the 'sorting_order' column of 'tasks' in the schema cache". This tool could never have pulled a task successfully since it was written.

Fixed in the same commit (2 references), and the sibling-ordering query aligned with the create_task convention — scoped by project_id + section_id, `(last?.sort_order ?? -1) + 1` instead of the stray `+ 1000`.

Worth noting for TDE-378/TDE-817: a tool that is 100% broken shipped undetected, which says something about how much of the 139-tool surface has never been exercised. That is a consolidation argument, not just a token one.
