PRINCIPLE: whenever a new task is created, its own `context`/detail should be self-contained by default — enough to pick it up and work it WITHOUT the surrounding chat, the agent's session memory, or external notes. That is the entire purpose of the task-context field.

WHY (lived example): TDE-304 was created with good what/why but the actual decision-to-make lived only in the conversation + local memory. It only became truly resumable "elsewhere" (new conversation / different machine / a teammate) after a "START HERE" block was appended INTO the task. The task is the only artifact that travels everywhere; chat and CC-local memory do not. So the bar is: a cold reader opening just this task can act.

SCOPE — applies to EVERY task-creation path:
- Agent create_task calls (don't write terse one-liners that assume the chat).
- bootstrap_project populate phase (concrete tasks, flow seeds, context seeds — seeds especially must carry their pre-brief + open questions, which they already aim to).
- resolve_seed output, flow task creation.

WHAT "self-contained" means in practice: the goal/why of THIS task, the key decision(s) or open questions if any, pointers to the load-bearing context (relevant files/KB/decisions), and the obvious next step. Not a transcript dump — the minimum a cold reader needs to act.

POSSIBLE ENFORCEMENT (decide during build): a standing ASSISTANT_DIRECTIVE ("write self-contained task context when creating tasks"); guidance in the create_task tool description; maybe a lightweight self-check/nudge. Lean toward directive + tool-description guidance over a hard gate.
