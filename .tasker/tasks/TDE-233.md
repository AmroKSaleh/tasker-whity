It doesn't make sense for a flow to be governed by rules that are project level. They need their own rules and instructions. Also, they must interact differently from how they normally do when they are project level.

--- AGREED DESIGN (2026-06-10) — Approach A. Full spec: docs/superpowers/specs/2026-06-10-flow-level-is-kb-design.md ---
Decisions:
1. IS precedence = REPLACE: a task in a flow with its own IS is governed by the flow IS; project IS is suppressed for it...
2. ...EXCEPT project IS entries marked universal:true (short IDs, deploy, code style) always apply. So a flow task sees universal project IS + flow IS.
3. Flow KB auto-injects on EVERY get_task for a flow task whenever the flow has KB (independent of IS).
Fallback: flow with no flow IS → full project IS.

Build: new tables flow_instructions + flow_kb (keyed by flow_id, cascade on flow delete); add universal boolean to project_instructions; new MCP tools get/list/create/update/delete for flow IS and flow KB (accept flow_id or task_id); add universal param to create_is_entry/update_is_entry; update get_task injection logic.
Out of scope (follow-up): app UI for flow IS/KB. MCP-first.
