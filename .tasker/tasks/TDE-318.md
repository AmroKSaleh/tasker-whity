The shipping-product version of the round-1 finding — independently valuable regardless of the experiment's verdict, so it can be done in parallel.

FINDING: Round 1 showed an adversarial / FAIL-prior validator over-rejects — it flagged false-positive "issues" on already-correct code and looped to the revision cap. Tasker's LIVE flow validation is designed the same way (the MCP directives state the validator "starts from a FAIL prior"), so it very likely shares this behavior in production: wasted tokens/latency on needless revision loops, and a real risk of "revising" already-correct output into something worse.

WHAT TO DO: recalibrate the live validator so PASS is reachable for conformant output. It should fail/▶revise ONLY on concrete contract-rule violations, not on style, naming, or hypothetical concerns, and should not grind to the revision cap on non-substantive issues. Keep enough adversarial rigor to catch real defects — the goal is the balance point (catch real violations, stop nitpicking correct work), which is itself a key product-design tension this experiment surfaced.

FILES: V2/supabase/functions/mcp/contract_gate.ts and index.ts — the validate_output path / the validator_agent_prompt / submit_validation_result logic. After changing, deploy MCP (supabase functions deploy mcp --no-verify-jwt) and add a KB note.

SANITY CHECK: run a known-good flow artifact through validation — the validator should PASS it without looping. Cross-references the experiment task "Calibrate the experiment validator" (same insight, different code).
