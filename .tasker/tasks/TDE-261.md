Feature: an independent judge agent that evaluates how a TASK was executed, at the task level (not only inside flows).

Why it matters: drift/hallucination is the default tendency of LLM execution, not an occasional bug — it's just usually invisible. A task-level judge makes conformance enforcement available to ANY task, not only tasks wired into a flow. (See KB entry "Case: Brand DNA Drift in Image Prompts — context placement &amp; conformance (2026-06-14)" — a task-level judge would have caught all four brand drifts at completion.)

Feasibility (summary): HIGH for output-judging — ~80% of the machinery already exists and is task-centric: set_task_output (a task's own bar, no flow needed), store_artifact (captures the real output, passed to the judge by the server for independence), validate_output + independent subagent + submit_validation_result (the judge loop), and the regenerate→retry→ask_human escalation policy. The net-new work is mostly orchestration: a task-level completion trigger, an opt-in flag, the check-vs-judgment split, and (the harder ~20%) execution-trace capture if we want to judge HOW it was done, not just the deliverable.

Each milestone below is an open question that must be resolved before/while building. Some examples the user called out: how time-consuming is it to set up review on one task, and what exactly does the judge compare the output against.

📐 DESIGN NOTE (2026-06-15) — reactive vs proactive judging:
- REACTIVE (current build): the executor never sees the bar; the judge grades AFTER and reopens on fail. The bar lives in review_bar; get_task does NOT inject it to the executor.
- PROACTIVE (future): show the executor the bar up front (inject review_bar into get_task for review-enabled tasks) so it conforms WHILE writing; the judge still backstops.
- Tradeoff: proactive = better first drafts, fewer cycles → better for PRODUCTION. Reactive = a clean draft-1 drift signal → better for MEASUREMENT.
- KEY REALIZATION: independence is NOT preserved by hiding the bar — a feedback loop leaks the failed rules after cycle 1 anyway (to fix a failure you must reveal the rule). It's preserved by the JUDGE's ALTITUDE (check intent, not the literal rule) + FRESHNESS (a new adversarial validator each cycle — which we already do). So the real lever is judge quality, not bar-hiding. The reactive-independence edge is really just "draft 1 is a clean drift signal."
- ANTI-GAMING: judge against intent not letter; frame critiques as deficiency-vs-intent, not a checklist to optimise against.
- DECISION: use REACTIVE for the comparison experiment (clean draft-1 drift), THEN switch the judge to PROACTIVE for production (surface review_bar to the executor via get_task) once the experiment is done. The proactive switch is a deferred follow-up.
