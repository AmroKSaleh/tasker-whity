Parked 2026-06-05 during the 137 design discussion. Worth designing later; NOT a 137 blocker.

## The idea
Attach a shared CONTEXT bag to a flow as a whole — distinct from per-task context. Some context is flow-wide, not task-specific: for an "article" flow, "this run is about X, for audience Y, tone Z, publishing on platform W" applies to every task in the flow. Today context only lives in each task's title/detail, so flow-wide context has to be duplicated across tasks (or lost).

## Why it's useful
- The grill-me interview (TDE-189) gathers a lot of flow-wide run context up front (especially the forward-mode grounding + the goal). That context needs a home — the flow level is the natural one.
- On template instantiation (152), the context poured into the blank slots is largely flow-wide ("this run is about…"). Storing it once at the flow level beats duplicating into every task.
- Refines the three-layer model (process / contract / context): CONTEXT itself splits into flow-wide vs task-specific. This task is about giving flow-wide context a place to live.

## The hard tension (the reason it's parked, not trivial)
We decided a flow is EMERGENT — a connected component of the I/O graph — NOT a stored entity with a stable ID (see KB "137 Contract Layer — Design Decisions" → Flow boundary & shape). So there's no obvious place to hang flow-level context. Options to weigh:
- (a) Make flows FIRST-CLASS entities (a `flows` table with an id) — contradicts "emergent," adds a real model change, but gives context a clean home + enables naming flows, listing them, etc.
- (b) Anchor context on a designated task (e.g. the terminal/goal task) — keeps flows emergent, but fragile (what if the anchor changes? what about disconnected sub-parts?).
- (c) Derive/key it by connected-component membership somehow — fragile as the graph mutates.
- The choice interacts with templates (152): a saved template is essentially "a flow + its flow-wide context blanked," so whatever holds flow context also shapes how templates serialize.

## Decision needed later
Whether per-flow context justifies promoting flows from emergent → first-class, or whether an anchor/derived approach suffices. Tee this up before building 152.
