Document and optimize for the user's primary workflow: "The way I use task mainly is that I do analysis or research and find what I gotta do, and I use the IDE I'm in to create a section inside the relevant project and populate it with tasks depending on the results and the recommendations of the AI." Ensure Tasker's MCP integrations and UI support this analysis-to-section-and-tasks workflow smoothly.

### Brainstormed Optimizations (2026-08-02)

1. **Tasker is a "Receiver" of batch work, not a manual entry tool**
   * **Optimization Idea (`create_section_with_tasks`):** Create a single MCP tool where the AI passes a JSON list of tasks, creating the section and all tasks in one swift API call. This saves tokens, time, and prevents the AI from timing out halfway through.

2. **The IDE holds the "Why", Tasker holds the "What"**
   * **Optimization Idea (Auto-Relay):** Instruct the agent (via the Project Instruction Set) to always write a summary of its research into the section's description, or into a master task's Relay Context, so the research isn't lost when the session ends.

3. **Handoff to Human**
   * **Optimization Idea (Deep Links):** Modify the MCP tools to return a clickable URL upon creation (e.g., `.../project/TDE?focus=section_id`). That way, the AI gives the user a direct link to review the section in the web app.

4. **Triage & "Draft" Tasks**
   * **Optimization Idea (Intake Panel):** Tie into TDE-395 (Conductor Triage). When an AI dumps a batch of tasks, they appear in a "Proposed" state in Tasker, giving the user a chance to click "Accept" or "Decline" before they officially clutter up the project board.

## PASS S2 (REAL WORK) — STILL OPEN. This is the remaining launch blocker.

S1 proves the mechanics work. It cannot tell you whether the workflow FEELS great, which is what the Phase-1 criterion actually asks. S2 is yours to run, on ONE genuine need — real research, real section, real tasks, in your own IDE, start to finish including reviewing it on the web board.

### The verdict must measure the PRODUCT, not the session (revised 2026-08-07)

The original criterion — "you finished without reaching for the web app to fix something the agent should have gotten right" — conflates two failures that feel identical in the moment and mean opposite things:

- **TOOL-GAP** — Tasker offers no way to do the thing, or actively makes it harder. Reproducible: it fails the same way for every agent, every session, every user. THIS is what S2 measures. Example from S1: create_task returns a UUID, so the agent cannot tell you what it just created without a second call.
- **AGENT-SLIP** — the model fumbled something the tools fully supported. Not reproducible: a different session gets it right. Example: forgetting to pass section_id when the parameter is right there.

Score the verdict on TOOL-GAPS ONLY. An unlucky session full of agent-slips is not a launch blocker, and letting it read as one parks the launch on a coin flip. Agent-slips still get logged — a cluster of them in one spot is evidence the tool's shape invites the mistake, which promotes it to a tool-gap — but they do not decide pass or fail on their own.

- **PASS** = a real analysis-to-populated-section round trip completed with ZERO blocking tool-gaps: you never had to open the web app to do something the MCP path should have been able to do, and never re-explained context the agent should already have had.
- **FAIL** = at any point it was faster to abandon the MCP path and do it by hand *because of a tool-gap*. Record WHERE. That point is the launch blocker — not the general feeling, and not the tally of slips.

### The grate log — fixed shape, filled in as you go

The deliverable is the log, and it is required even on a pass; a clean pass with an empty log means the log was not kept. Do not invent a format mid-session — that friction is how hand-kept logs die. One block per hesitation, in the order they happened:

```
#<n> [tool-gap | agent-slip]  <where — the tool call, screen, or moment>
  Expected:  <what you thought would happen>
  Happened:  <what actually did>
  Cost:      <seconds lost / extra calls / had to open the web app / abandoned MCP>
```

A hesitation is worth a block if you paused, re-read something, backtracked, or reached for the web app — even briefly, even if you then carried on. Classify at the moment you write it, while the reason is still fresh; retro-classification drifts toward blaming the tool.
