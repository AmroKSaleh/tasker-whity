FOUND 2026-07-28 while building a throwaway guide flow to test TDE-821's advance_guide recording. Not a hypothetical — it blocked a legitimate flow.

THE PROBLEM: `name_flow` refuses to finalize a flow unless EVERY internal handoff carries a non-trivial, human-blessed contract on both sides. Actual response:

  {"status":"contract_gate_failed","blocked":true,
   "message":"Cannot finalize flow \"…\": 2 contract issues. Each internal handoff needs a
    non-trivial, human-blessed contract on both sides. Sharpen the flagged rules, then run
    confirm_contract on each side, and retry. To finalize anyway against your own judgment,
    re-call with bypass: true (and bypass_reason) — the flow will be permanently recorded as
    gate-bypassed.",
   "violations":["#824 → output def-of-done: no rules (empty contract)",
                 "#825 ← input from #824: no rules (empty contract)"]}

WHY THIS IS WRONG NOW: it directly contradicts the definition settled 2026-07-28 and already written into the MCP directive by TDE-808 — "CONTRACTS ARE OPTIONAL — they are a property of certain joins, never the definition; a flow with no contracts anywhere is still a flow." TDE-813 fixed the same assumption in the Flows UI (ungated flows were invisible, copy treated gates as mandatory). The MCP's own FINALIZATION gate was never updated, so the three surfaces now disagree: the directive says contracts are optional, the UI accepts ungated flows, and name_flow refuses to create one.

THE REAL COST: the only way through is bypass:true, which "permanently records the flow as gate-bypassed." So a correctly-designed ungated flow — per the current definition, an entirely valid thing — is branded a bypass for life. That is a false record, and it will poison exactly the gate/contract analytics TDE-784 wants to build ("here's proof our gates work" is worthless if legitimate ungated flows are indistinguishable from someone skipping a gate).

WHAT TO DECIDE (do not just delete the gate):
- Should name_flow warn instead of block when handoffs have no contracts? The definition says gate only at SEAMS, and "not every handoff is a seam" — so no-contract is the correct default for most joins, not a violation.
- Is there any case worth still blocking on? Possibly a contract that EXISTS but is trivial/unsharpened (the original intent) — as opposed to deliberately absent. Those two cases are currently conflated into one error.
- The bypass record needs a distinct meaning: "gate deliberately not needed here" is not "gate skipped". Existing flows recorded as gate-bypassed may need reinterpreting.

VERIFY WITH: create two linked tasks with no contracts, call name_flow, expect it to succeed (or warn) rather than requiring bypass. Cross-ref TDE-808 (directive rewrite), TDE-813 (UI fix), TDE-784 (moat analytics that consume this signal), and the memory "Flows redefinition — AGENDA COMPLETE".
