Split out of TDE-343 on 2026-08-04. TDE-343 had fused two different things — a MEASUREMENT of whether the core workflow feels great (the Phase-1 launch blocker) and this OPTIMIZATION BACKLOG (four ideas brainstormed 2026-08-02). Fusing them made "does TDE-343 block launch" unanswerable, because the optimizations cannot all ship before launch and the measurement can. TDE-343 keeps the measurement; the candidates live here.

Filed as a SEED, not a task, because the S1 measurement changed which of these are worth building and two of them are now questionable. Resolve this seed only after the real-work pass on TDE-343 is done — that pass supplies the "feel" evidence this seed's open questions need.

THE FOUR ORIGINAL CANDIDATES, RE-JUDGED AGAINST MEASURED EVIDENCE (S1, 2026-08-04 — a 10-task section populated in project AAA, section "Measurement Run S1"):

1. `create_section_with_tasks` (batch creation) — WEAKENED, probably not worth building. Its stated justification was saving tokens/time and stopping the AI "timing out halfway through." Measured: the 10 create_task calls were issued CONCURRENTLY in a single message, so wall-clock was about one round-trip, not ten, and nothing was at risk of timing out. And token cost is dominated by the REQUEST — the task titles, details, and milestones, which must be written either way — not the responses, which are two lines each. Real saving is protocol framing only, well under 1k tokens on a 10-task batch. Compare the ~27k of redundant tokens from the get_task context bug found in the same pass. Build only if a specific client that cannot parallelize tool calls is a target.

2. Auto-relay (agent writes its research into the section description or a master task's relay_context) — UNTESTED by S1, still open on its merits. S1 measured mechanics, not whether the "why" survives. The real test: open a created task cold in a fresh session with no chat history and see whether it is actionable — which is the TDE-305 self-contained-context rule, and IS checkable. Note that Tasker has no section description field today, so the master-task variant may be the only cheap version.

3. Deep links (MCP returns a clickable URL on creation) — CONFIRMED as real friction, and a much cheaper sub-fix was found. create_task returns ONLY `id: <uuid>`. It does not return the short ID. Learning that the batch became AAA-1..AAA-10 required a whole extra list_tasks round-trip, and without it the agent cannot even tell the human which task IDs it just made. So: RETURN THE SHORT ID IN THE create_task RESPONSE is a tiny fix that removes a round-trip and delivers most of the value; the full clickable-URL version is a separate, larger question. Do the short ID first regardless.

4. Intake / "Proposed" state panel, tied to TDE-395 — UNCHANGED, and the biggest of the four. S1 says nothing about it. Note the tension worth resolving before building: a Proposed state adds a triage step to a workflow whose whole appeal is that the agent populates the board in one shot. It may be solving a problem the human does not have.

ALSO MEASURED IN S1, no action needed but worth knowing: 10/10 tasks landed in the intended section with priorities and milestones intact, so the TDE-369 class of bug (section_id written null, task invisible on the board) did not recur through the MCP path. The TDE-379 similarity check produced ZERO false refusals across ten thematically-related tasks — it did not obstruct a legitimate batch.
