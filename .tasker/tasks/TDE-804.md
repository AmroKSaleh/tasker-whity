What if a project has multiple phases? Give the user the ability to split a project into multiple stages, where each one has its own progress bar. Make it so that the "Total" progress bar can be clicked, and when the user does so, it splits into smaller bars that each represents its own progress. There should be UI that changes the phase focus of the project, changing the color of the project, to make it obvious to the user.

---

## Design review — 2026-07-27 (agent, user broadly agreed)

**Verdict: real need underneath, but the description above is the wrong half of the feature. Do not build as written. Blocked on one decision (see bottom).**

**Collides with the TDE 3-way project split.** The canonical 3-phase model (P1 core hub+MCP → LAUNCH, P2 post-launch business/RBAC/teams, P3 Local Mode fork) is currently being expressed by splitting TDE into three separate projects — a plan that exists precisely *because* there is no phase primitive. This task is the competing solution to the identical problem, not a complement to it. If phases ship, sharding TDE is redundant; if TDE is sharded, TDE itself stops needing phases. Read: the split is right for TDE specifically (three phases with genuinely different Foundations, instruction sets, and audiences deserve separate boards), while phases are right for the *product* (most users won't shard a project to express "v1 / v2 / later"). Both can be true — but then this feature is built for other users, not for dogfooding, which lowers how much it deserves.

**The task is all chrome, no concept — the biggest gap.** Everything described is a progress bar and a color. Nothing defines what a phase *is* in the data, and nothing touches MCP. That fails the project's own AI-native test. "What's in scope right now?" is exactly the question an agent must currently be told in prose every session. Phases that exist for the human but not the agent create a new way for human and AI to disagree about scope — the precise friction the positioning commits to collapsing. `get_ready_work` filtered to the active phase is worth more than the segmented bar.

**Cut the color mechanic.** Recoloring the whole project per phase fights two shipped things: Environments already own a color column (project color carries environment identity), and the editorial palette's paper→line contrast ramp was deliberately re-spaced (TDE-353). Replace with a phase *badge* beside the project name plus the accent applied only to the active segment of the bar — same "obvious which phase I'm in", far less risk.

**Don't call it "focus".** Focus Mode is a disabled stub pending a rethink (TDE-351) and section focus is a live separate concept. A third meaning of the word will cost more than it saves. Use "active phase" / "current phase".

**Data model: phase must be a field on the TASK, not on the section.** Sections-own-phases is cheaper (one field, no migration) and superficially fits, but the real 3-phase sort cuts straight *through* the Core App section — its open tasks contain both P1 launch-critical and P2 post-launch business work. The sorting key ("is this advantageous to the single user?") is a per-task judgment, not a per-section one. The segmented bar is then a `group by phase` over tasks.

**Progress math inherits TDE-806.** Flow steps leave the denominator entirely (TDE-320) — per-phase bars must apply the same `flow_id is null` filter, and any new cached hook feeding them needs a versioned cache key. See KB "Bug: /projects card counted flow steps".

**Click-to-split is a disclosure gimmick, not the design question.** The real question is the default state: a project with phases should probably show the segmented bar by default (one stacked bar with dividers) rather than hiding structure behind a click. Also unresolved: does this live on the project card, the project header, or both? Card space is already tight.

**Priority: lower than it feels.** Phases pay off on large, long-lived boards. The target user's first project has 20–40 tasks and one phase, and the Foundation names "scope creep on features before monetization" as a top risk. This is a feature a 250-task dogfooder would love — not one the first 10 paying users need. Recommendation: post-launch.

**Shape if/when built:** `phase` field on task + MCP exposure (read the active phase, filter ready work by it) + segmented progress bar grouped by phase + phase badge. No whole-project recolor.

**OPEN QUESTION (blocking — do not start work until answered):** is this feature meant to *replace* the 3-way TDE project split, or to live alongside it?

## RESOLVED SPEC — 2026-07-27 (supersedes the review above; build this)

The review above rejected the *original* description (per-task phase stamps + click-to-split bar + whole-project recolor) and asked one blocking question. Both are now settled. The blocking question is answered: phases live ALONGSIDE the TDE/TG/TLMV project split, because migrating tasks between projects was rejected — `move_task` reassigns `short_id` (orphaning every TDE-xxx reference in the KB, git history and branch names), unlinks flows and drops cross-boundary I/O edges. A phase is functionally a sub-project WITHOUT that cost. See memory `phase_model` and KB "Move tasks across projects".

### What a phase IS
A stage of a project bounded by an **exit condition**, not a date. "Phase 1 ends when we launch." A deadline is OPTIONAL decoration. This is what distinguishes a phase from a sprint/cycle, which is bounded by the calendar and repeats uniformly. Cycles (TDE-785) are a DIFFERENT primitive — time-boxed, sprint-shaped, in the conceded human-coordination lane — and are not a substitute for this. TDE-785 should close as already-covered per its own next step.

The `exit_condition` field is the honesty guardrail, not decoration: writing "this phase ends when X" forces a statement of what is actually REQUIRED, so anything unrequired falls out to a later phase. Phases motivate legitimately when they REDUCE committed scope, and deceptively when they merely re-slice the same scope. Without the exit condition the temptation is to distribute tasks evenly across three buckets and change nothing but the readout.

### Origin / why this is worth building
An external user (not the owner) with a very large Tasker project reports feeling he makes no progress. The instrument is too coarse: at 300 tasks, closing one moves the bar 0.33% — below human perceptual threshold. At 100 it is 1%. Same work, visible movement (goal-gradient effect). This is the first non-founder demand signal for the feature, and it is what moved it from "post-launch chrome" to worth building.

### Behaviour
**Whole-project view (default):** shows ALL tasks including unphased. Aggregate progress bar built from the phase totals PLUS an explicit unphased segment. The aggregate view must stay default and visible — hiding it is what turns a progress indicator into a morale trick (phase 1 at 85% while the project is at 30%).

**Phase view:** navigating into a phase shows ONLY that phase's tasks (normal sectioned board, filtered), the progress bar/tracker scopes to that phase, and the page background takes a slight tint as an ambient "different context" signal.

**Unphased tasks are first-class and permanent, not a triage queue.** `phase_id` nullable; no auto-stamping. Null is the honest state — a wrongly-stamped task lies, an unstamped one admits it is unsorted. Plenty of work legitimately never belongs to a phase (idea inventories like the Mined Ideas section, evergreen work). Marked with a ribbon/indicator on the card in the whole-project view, shown inline in their sections (NOT hoisted into a separate column — they need section context), plus a count as its own segment in the aggregate bar so the pile stays measurable.

v1 deliberately does NOT distinguish "deliberately phase-agnostic" from "not yet sorted" — a second nullish state earns its keep only after the pain is felt. Revisit if the unphased pile becomes noise in practice.

### Constraints / decided rejections
- **NO whole-project recolor.** A slight background tint on the phase view only. Tints MUST be derived from the existing paper→line ramp (deliberately re-spaced for contrast in TDE-353) — arbitrary hues will break text legibility. Tinting only reads for ~4-5 phases; beyond that the badge carries identity.
- **NO click-to-split bar.** Navigation IS the disclosure mechanism — the bar's scope follows where you are. One less piece of UI state.
- **Do NOT name anything "focus"** — Focus Mode is a disabled stub (TDE-351) and section focus is a separate live concept.
- Progress math inherits TDE-320/TDE-806: flow steps leave the denominator (`flow_id is null`), and any new cached hook needs a versioned cache key.

### Agent-facing half (this is what makes it more than a progress bar)
"What is in scope right now" is currently answered by prose in the Foundation every session. As a structured field the agent is better grounded on every task it opens.
- Expose the phase on `get_task` / `get_project`; `list_tasks` filterable by phase; set/advance the active phase over MCP.
- `get_ready_work` scoped to the active phase, BUT **unphased tasks stay in the queue regardless of phase scope**, ranked below phased work, with the response stating how many unphased items it included. Otherwise an unphased launch-blocker is in no phase, therefore in no queue, therefore unreachable — and the phase view hides it from the human too.

### Do in parallel, not instead
TDE-385 (durable-state hygiene: auto-archive, stale flags). A large share of "I never make progress" is dead weight inflating the denominator. Phases fix the resolution; hygiene fixes the denominator.
