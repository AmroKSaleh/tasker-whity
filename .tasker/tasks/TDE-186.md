Missing capability discovered during use (2026-06-04): there is no way to move a task to a different project. update_task only relocates a task within the same project (between sections/groups via section_id/group_id); there is no project_id on update_task and no dedicated cross-project move. Result: "migrating" tasks between projects today means recreate + delete, which loses dependency wiring and is laborious.

Build: a move-task-across-projects operation (single task and ideally bulk/section), preserving detail, priority, status, and ideally remapping or warning about input/output dependency edges that cross the boundary.

———————————
📌 REVIEW NOTE (2026-06-13): Difficulty = MODERATE. Straightforward part: move a single task + preserve detail/priority/status. Hard part: handling I/O dependency edges that would cross the project boundary. Recommended phasing — (1) single-task move that warns-and-drops cross-boundary edges, (2) bulk/section move + edge remap later.



---
PHASE 1 BUILT (2026-06-25), pending live verification after CC restart.
- New MCP tool `move_task(task_id, target_project_id, target_section_id?)`.
- Reassigns short_id into target project's sequence (BEFORE INSERT trigger doesn't renumber on UPDATE, so computed manually as MAX+1 — small race, acceptable for single-user).
- Unlinks flow (flow_id/flow_step null), resets section/group (project-scoped), validates optional target section belongs to target project.
- Warn-and-drop cross-boundary edges: drops the task's own input edges AND strips it as a source from downstream consumers left behind. Response reports exactly what was dropped.
- Decision: MCP-only for Phase 1 (user chose). Phase 2 (deferred): bulk/section move + edge remap instead of drop.
- Deployed to MCP. NOT verified live yet.
