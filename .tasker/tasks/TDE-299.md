Extend bootstrap_project so a created project comes out POPULATED and ready to work — not a grounded shell. Designed with the user (follows TDE-262 Foundation work).

Output of bootstrap = Foundation + a populated board, where every work item is sorted by how ready it is to commit:
- CONCRETE TASK — path is clear from the ratified Foundation; created and placed in its real section now.
- FLOW SEED — multi-step, contract-linked process; can't be a flat task (needs build_new_flow's contract interview). Parked in a "Suggested Flows" section.
- CONTEXT SEED — known to be needed but underspecified; parked in a "Needs Context" / "To Define" section instead of fabricating fake precision.
Plus: KB seeded from real decisions made during the interview; IS proposed (existing step).

UNIFIED SEED MECHANIC (the key primitive):
- A Seed is a task whose DELIVERABLE is another Tasker artifact, produced once the user resolves its open context. Target type: `task` or `flow`.
- Seed detail carries: rough subject, the SPECIFIC open questions blocking specification, and why it's needed (so resolution is a short targeted react-interview, not a cold restart).
- Resolution = the agent runs the mini react-interview to produce a spec, then ONE atomic operation materializes it:
  • context seed → resolve_seed(seed_id, task_spec): creates the concrete task, places it in the correct section/group, closes the seed.
  • flow seed → build_new_flow with the seed's pre-brief.
- Provenance: spawned artifact links back to its seed (spawned_from_seed_id) — reuse the Conductor provenance pattern (tasks.intake_source/intake_job_id). Seed isn't lost; it's the audit trail.
- Mark seeds clearly so the agent treats "completing" a seed as "resolve → spawn", not "do the work directly".

GUARDRAILS (all from the session's recurring principle — propose/ratify what's legitimately known, don't fabricate depth the input can't support):
- Be sparing with seeds — most near-term work should be concrete; avoid a "seed graveyard". Surface a count so seeds don't rot (same instinct as the Conductor parked-count badge).
- Populate as an opt-in step AFTER Foundation ratification, react-to-draft, ONE ratify pass — not a silent auto-spew, not a mega-ceremony.
- "Needs Context" section is distinct from the auto-created Backlog (Backlog = not-yet-prioritized; seed = can't-be-specified-yet).

This is becoming a core Tasker idiom: capture insight at peak context, defer commitment until it can be done well (same shape as the Conductor's parked intakes).
