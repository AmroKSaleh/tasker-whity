Idea originated in a WQW (Waqtak Website) session on 2026-07-02 while working the "Audit Results" section. On WQW-70 (a copy fix on a live page), the user said "the website is updated" and asked to mark it done, but a fresh fetch of the live page still showed the old text. Only after retrying with a cache-busting query param did the fix show up live. Marking the task done on the user's word alone would have closed it while it was still actually wrong. The agent instead fetched the live URL, caught the mismatch, retried, and only called complete_task once the fetch matched the expected content. Same pattern was repeated on WQW-71 (verifying 3 edited blog posts before completing). The user confirmed they want this to be a repeatable practice, not a one-off.

The problem: complete_task currently trusts whatever the executing agent/user asserts. For tasks whose deliverable is a checkable external artifact (a live webpage, a deployed file, a pushed commit, an API response), there's no structural mechanism forcing a check of that artifact's actual current state before the task is marked done — it relies on the agent remembering to verify, which won't happen by default in every session/every agent.

Proposed direction (not fully specified, needs design): Tasker already has the right primitive for this in flows — output contracts with kind=check rules that require observed_value evidence (see the CHECK RULE EXECUTION directive: the agent must submit the raw observed datum, e.g. a fetched page's actual text, not just assert compliance) before submit_validation_result can pass. Extend that same mechanism to plain (non-flow) tasks: when a task's deliverable is a checkable live artifact, attach a check-rule-style contract (e.g. "fetch URL X, confirm text Y is present") and block complete_task until that check has been run and passed, the same way flow steps are already gated.

Two possible levels to solve this at, worth deciding between during design:
1. Lightweight / immediate: encode "verify live edits before completing" as a per-project Instruction Set (IS) entry (the same mechanism already carrying WQW's "Article release flow is mandatory" and "no em dashes" rules) — this is a convention, not enforced by the server, relies on the agent reading and following project IS entries.
2. Structural / enforced: a real task attribute or contract type that requires an observed_value check to be submitted (similar to flow output contracts) before complete_task succeeds server-side, regardless of whether the agent remembers to do it. This is the version that "survives" even if the agent working the task next time doesn't know this pattern exists.

Related existing TDE tasks in this same section (Core App): task types (Discussion/Execution) to modify default behaviors, and optimizing Tasker for the user's actual "how I use Tasker" workflow — this fits the same theme of task-type-driven default behavior differences.

Next step: design discussion with the user on which level (IS convention vs. enforced contract) to build first, and whether this becomes a new task "kind" or an optional contract attachable to any normal task.

WHY (positioning): AI code churn is an acceptance-discipline problem; the verify-before-complete gate is the lever (IS only fixes generation). This gate = Tasker's moat made concrete. Full rationale in KB "Product: AI code-churn — IS + verification gate as ONE system (TDE-365)".
DECIDED DESIGN:
- Scope the gate to standalone AI-executed tasks (executor=agent), NOT just full flows.
- DEFAULT-SUGGESTED, ONE-CLICK, SKIPPABLE — toggle defaults ON for agent tasks, user can skip; do NOT hard-mandate (avoids rubber-stamp fatigue).
- PREFER deterministic kind=check gates (tests/build/lint/file/word-count) over human-judgment gates — a gate that needs a human to approve decays into rubber-stamping. Reuse the existing check-rule + store_artifact/validate machinery; judgment path via TDE-261 judge only where no check fits.
- Core App must show "done" vs "done + verified" distinctly: completing an agent task with no passing gate renders as "done (unverified)", not silently green.
NEXT: spec the minimal task-level gate data model + the UI (one-click add on a task, the unverified badge) building on existing contract/review machinery.
