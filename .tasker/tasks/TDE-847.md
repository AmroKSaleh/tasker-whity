On 2026-07-31, a routine redeploy of the `mcp` Supabase Edge Function (to add TDE-782's tags fields) shipped without the `--no-verify-jwt` flag. This caused Supabase's platform gateway to reject every request lacking a real Supabase-signed JWT — breaking the MCP for every Tasker user (the app's custom bearer-token auth scheme isn't a Supabase JWT). Fixing that exposed a second, deeper bug: `getScopedClient()` (from TDE-780's MCP authorization hardening) requires a signing secret via `Deno.env.get('SUPABASE_AUTH_JWT_SECRET')` — a name Supabase's CLI structurally refuses to let you set (`SUPABASE_` prefix is reserved), so it had never actually been configured. Renamed to `AUTH_JWT_SECRET` and wired to the project's legacy HS256 JWT secret (Settings → API → JWT Keys → Legacy JWT Secret tab — NOT the Key ID shown on the main JWT Signing Keys tab, which is for the new asymmetric ECC/RSA keys and cannot sign a verifiable HS256 token).

Both bugs caused a TOTAL outage of every tool call, for every user, for roughly 2+ hours before anyone noticed — because nothing checks the function's health after a deploy. The failure mode was fail-closed (tool calls errored instead of silently bypassing RLS), so there was no cross-tenant data exposure — but availability broke silently for the whole user base.

Goal: add an automated check that runs immediately after every `supabase functions deploy mcp` (or manually invokable) that would have caught both failure modes in seconds instead of hours:
1. POST to the mcp endpoint with NO Authorization header and confirm the response is a normal JSON-RPC response (not a gateway-level 401 — this catches a missing `--no-verify-jwt`).
2. POST a `tools/call` for a cheap, safe, real tool (e.g. `get_my_attention` or `list_projects`) using a valid test API key and confirm a 200 with no `SUPABASE_AUTH_JWT_SECRET`/`AUTH_JWT_SECRET`-style error in the body (this catches a broken/missing scoped-client secret).

Open question: whether this becomes a standalone script (`scripts/smoke-test-mcp.sh` or similar) that's part of the deploy habit, or gets wired into a lightweight CI step. Given deploys are currently manual (`supabase functions deploy`), a local script that's part of the deploy checklist is the pragmatic v1 — CI wiring can follow if deploys ever get automated.
