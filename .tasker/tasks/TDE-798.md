## OUTPUT — there are NO flow types (settled 2026-07-28)

A negative result, and a load-bearing one: **the taxonomy this task asked for does not exist.** Every candidate raised across three separate questions collapsed under Q2's razor (a real type must change how the WHOLE operation is handled). What looked like types are one of three other things: a per-step attribute, an authoring heuristic, or a rendering requirement.

### Every candidate, and how it died

**Gate kind (check / judgment / multi-vote) — DEAD.** This was the task's own favourite ("the axis that matters most — it maps to cost AND to TDE-212"). Q5 killed it: gate kind is chosen PER SEAM. One flow legitimately carries a deterministic check at one boundary, no gate at the next, and an independent judge at the terminal output. A property that varies inside a single flow cannot characterise it. Identical failure mode to "sequential vs connected" in Q2 — a per-seam attribute wearing a whole-flow costume.

**Shape (linear / DAG / revision-loop) — already demoted in Q2.** Real, but not a type.

**Executor (AI / human / mixed) — DEAD, reversing Q2.** Q2 passed this as the one axis that survived the razor. Q4 and Q5 sharpened the razor enough to see it fails too: `executor` is a **per-step attribute** that already exists on the step, and mixed flows are the normal case. "A human-executed flow" is not a kind of flow — it is a flow where every step happens to have `executor: user`. Emergent property of the parts, not a property of the whole.
The user's framing of the same point: executor makes no difference **at build time, only at execution** — and that runtime branch is already shipped as `guide_flow`/`advance_guide` vs `run_flow`, keyed off the per-step attribute. No type is doing any work there.

**Homogeneity — batch vs process (Q3 candidate) — DEAD.** It is Q3's cutting rule doing its job while you author. Nothing in the system branches on it afterwards.

**Determinacy — known chain vs discovered (new candidate) — DEAD.** A flow that discovers its own steps simply has steps added during the run. No type needed; the only real consequence is a rendering one (below).

### What this forecloses (the practical payoff)
No `flow_type` column. No type dropdown in the create-flow UI. No per-type branching in the MCP or the runner. Three separate questions generated five candidate types and all five collapsed under the same razor — decent evidence the razor itself is sound.

### The one concrete requirement that falls out
**Progress display must stay honest when steps are added mid-run** — a readout must not claim "3 of 7" when the 7 is not knowable. A UI honesty requirement, not a taxonomy. Not yet a task.

### Note on method
Q2 passed executor; Q6 overturns it. That is the agenda working as intended — later questions sharpened the razor and it cut something an earlier question had let through. The razor is now: *does this vary inside a single flow? Then it is not a type.*
