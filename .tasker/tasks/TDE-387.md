From Linear: attachments are {title, subtitle, url, iconUrl, metadata} objects where the URL IS the idempotency key — re-creating with the same URL updates in place, "enabling stateless applications" that store no attachment IDs; attachmentsForURL answers the reverse question (given a PR URL, which issues own it); agent sessions carry labeled externalUrls deep-linking to PRs/dashboards.

Build: a labeled-links array ({label, url}) on tasks and task outputs; URL as idempotency key so agents can blindly re-link every run without creating dupes; a reverse-lookup MCP tool ("which task owns this PR/doc URL?"); links rendered clickable on task cards and the detail panel (PR, deployed URL, Drive doc, report).

This is the data mechanism BEHIND TDE-313 (task cards list attached/connected items) — build this first, TDE-313's display work consumes it. Also feeds the magic-words loop (PR link attaches to the task it closes) and store_artifact/set_task_output (close cousins today, no first-class link metadata).
